# Permission States

権限や契約プランによって利用できない機能を、業務との関係と情報公開の安全性に応じて扱う。表示しない、無効にして理由を示す、閲覧だけにする、のいずれかを選び、すべてを機械的に非表示や無効にしない。

状態：初期実装（レビュー前。v0.1 確定ではない） ・ 実装：[`registry/patterns/access-decision.ts`](../../../registry/patterns/access-decision.ts)、[`registry/patterns/access.ts`](../../../registry/patterns/access.ts)、[`registry/patterns/restricted-action.tsx`](../../../registry/patterns/restricted-action.tsx)、[`registry/patterns/access-state.tsx`](../../../registry/patterns/access-state.tsx) ・ 全体：[System & Account](system-and-account.md)

## 目的

利用者が「なぜ使えないのか」「何をすれば使えるのか」を、考えなくても判断できるようにする（原則 01）。利用できない機能で画面を複雑にせず（基本思想）、必要な機能と解決の方法は削らない（原則 08）。UI の制御は、利用者に結果を伝える手段であり、バックエンドでの認可の代わりにならない。

## 使用条件

- ロールの権限（認可）、契約プラン（Entitlement）、前提の設定、処理中、接続、サービスの状態によって、操作や情報の利用を制限するすべての画面に適用する。
- ページ全体にアクセスできない場合（ログインが必要、閲覧の権限がない、存在しない）は、`AccessState` を使う。
- データの取得の失敗、再取得、欠損は [Data States](data-states.md) に従う。障害、メンテナンス、オフラインの表示の位置は [System States](system-states.md) に従う。

## 構成

| 部分 | 部品 | 仕様 |
| --- | --- | --- |
| 権限の取得 | `useAccess`（`access.ts`） | スコープ（`scopeKey`）の権限と契約プランの機能を取得し、`loading`、`error`、`refreshing`、`stale`、`ready` を返す。内部で `useBrowseData` を使う。`error` は同じスコープの前の権限がない場合（初回の取得の失敗）だけ |
| 操作の判断 | `decideAccess`（`access-decision.ts`。以下の判断の関数も同じ） | 必要な権限、機能、前提の設定、サービス、接続、処理中から、許可するかと理由（`Restriction`）を返す |
| 画面での扱い | `presentAction` | 判断の結果と操作の性質（業務の操作か管理の機能か、存在を知らせてよいか、申請できるか）から、`enabled`、`disabled`、`hidden` を返す |
| 内容の扱い | `resolveContentAccess` | 閲覧と変更の権限から、`edit`、`read-only`、`hidden`、`pending` を返す |
| 制限された操作 | `RestrictedAction`（`restricted-action.tsx`） | `hidden` は描画しない。`disabled` は理由の文を操作のすぐ後に表示し、`aria-describedby` で関連付ける。無効の操作もフォーカスできる |
| セクションの説明 | `RestrictionNotice` | 複数の操作が同じ理由で制限される場合に、セクションの先頭に 1 つだけ置く（既存の Alert） |
| ページのアクセス | `AccessState`（`access-state.tsx`）、`pageAccessFromStatus` | ログインが必要、閲覧の権限がない、存在しない。既存の Empty を使い、移動先と解決の方法を `actions` に置く |
| フォーカスの移動 | `useFocusRecovery` | 権限の変更で、フォーカスしていた操作が描画されなくなった場合に、変更を知らせる見出しへ移す |
| 閲覧専用の表示 | 組み合わせの例（`dl`、Read Only の Input） | 通常の文字で表示する |
| Permission Matrix | 組み合わせの例（既存の Table） | ロールごとに、実際にできる操作を示す。ロールと権限は製品のデータとして渡す |
| ロールの変更の確認 | 組み合わせの例（既存の Alert Dialog） | 影響の大きい変更だけ、できるようになる操作とできなくなる操作を示して確認する |

| 対象 | 扱い | 例（プレビュー） |
| --- | --- | --- |
| 業務に関係のない管理の機能 | 表示しない | 閲覧者とメンバーに「メンバーを招待」「監査ログ」を表示しない |
| 存在を知らせてはならない機能・情報 | 表示しない。件数、検索の候補、書き出し、通知にも含めない | 担当者だけが閲覧できる顧客を、件数と検索の結果に含めない |
| 利用者が必要とする可能性がある操作 | 無効にし、理由と解決の方法を示す | 閲覧者の「顧客を編集」 |
| 閲覧できるが変更できない | 閲覧専用（通常の文字） | 閲覧者の顧客の詳細、メンバーの組織の設定 |
| 権限を申請できる | 必要に応じて表示し、申請を示す | 「メンバーを閲覧」の申請 |
| 権限を確認できていない | 許可しない。業務の操作は無効にして「確認しています」、管理の機能は表示しない | 権限の取得中と取得の失敗 |

「業務に関係するか」は利用者ごとに決まる。管理の機能でも、その権限を持つ利用者（管理者）には業務に関係するため、契約プランで利用できない場合は無効にして理由を示す（`Restriction` の `entitlement` の `missing` が空の場合）。

### 制限の理由

理由は、内部でも別の状態（判別可能なユニオン `Restriction`）として持ち、すべてを「権限がありません」にしない。

| `kind` | 原因 | 既定の文（`restrictionText`） | 解決の方法の例 |
| --- | --- | --- | --- |
| `unresolved`（`loading`） | 権限の取得中 | 権限を確認しています | なし（待つ） |
| `unresolved`（`error`） | 権限の取得の失敗 | 権限を確認できませんでした。確認できるまで、この操作は行えません | 権限を再確認 |
| `unresolved`（`refreshing`） | 権限の変更の知らせを受けて再確認中 | 最新の権限を確認しています | なし（待つ） |
| `unresolved`（`stale`） | 再確認の失敗 | 最新の権限を確認できませんでした。確認できるまで、この操作は行えません | 権限を再確認 |
| `entitlement` | 契約プラン | 〈機能〉は、現在の契約プランでは利用できません | 契約を変更できる利用者：契約プランを確認。できない利用者：問い合わせ先 |
| `authorization` | 認可（ロールの権限） | この操作には「〈権限〉」の権限が必要です | 申請（申請できる権限だけ）、または管理者への問い合わせ |
| `prerequisite` | 前提の設定の不足 | 〈設定〉を済ませると利用できます | 自分で変更できる設定への移動。できない場合は問い合わせ先 |
| `service` | サービスの障害、メンテナンス | 障害のため、この機能は一時的に利用できません | なし（System States の表示に従う） |
| `connectivity` | 接続（オフライン） | オフラインのため利用できません。接続が戻ると利用できます | なし |
| `pending` | 処理中 | 処理が終わるまで操作できません | なし |

判断の順序：権限の未確定 → 契約プラン → 認可 → 再確認中・再確認の失敗 → 前提の設定 → 障害 → 接続 → 処理中。

- 契約プランを認可より先に判断する。権限を申請しても、契約プランで利用できなければ解決しないため。
- 構造的な理由（契約プラン、認可、前提の設定）を、一時的な理由（障害、接続、処理中）より先に判断する。「オフラインのため」と示した後、接続が戻っても権限がないために使えない、という誤解を避けるため。

## バリエーション

### 閲覧専用

- 閲覧だけを目的とする画面は、項目名と値の文字（`dl`）で示す。すべての Input を Disabled にする構成を標準にしない。Disabled の Input は文字が薄くなり（`opacity: 50%`）、閲覧できる情報の視認性を下げる。
- 一部の項目だけ変更できない場合（編集の画面の「顧客 ID」）や、コピーが必要な値は、Read Only の Input（`readOnly`）にする。Input の `read-only:not-disabled:bg-muted` で区別し、文字は薄くしない。
- 閲覧専用の理由は、セクション単位で 1 回示す（`RestrictionNotice`）。項目ごとに繰り返さない。

### 無効化の理由

- 理由は、操作のすぐ後に文で表示する。Tooltip だけに入れない（Base UI の Tooltip はタッチで開かず、ポインターを重ねないと読めない）。
- 無効にした操作も、Tab でフォーカスできる（Base UI の Button の `focusableWhenDisabled`。`aria-disabled="true"` になる）。理由は `aria-describedby` で関連付け、操作に移動したときに読み上げられる。
- 複数の操作が同じ理由で制限される場合は、セクションの先頭に `RestrictionNotice` を置き、その `id` を各操作の `describedBy` に渡す。
- 鍵のアイコンや色だけで状態を伝えない。理由の文を必ず置く。

### ページへのアクセス

| 状態 | サーバーの応答 | 表示 | 移動先と解決の方法 |
| --- | --- | --- | --- |
| ログインが必要 | 401 | 「ログインが必要です」 | ログイン。ログインした後、同じページに戻る |
| 閲覧の権限がない | 403 | 「このページを表示する権限がありません」 | 一覧など閲覧できるページへの移動、問い合わせ先（申請できる権限なら申請） |
| 存在しない | 404 | 「ページが見つかりません」 | 一覧など閲覧できるページへの移動 |

- HTTP のステータスコードだけを表示しない。必要な場合も、状態の文の補足にとどめる。
- 対象の存在を明かすことが情報の漏えいになる場合は、権限不足を不存在と同じに扱う。

| 権限不足を不存在と同じに扱う | 権限不足として示す |
| --- | --- |
| 対象の存在そのものが機密である（担当者だけが閲覧できる顧客、非公開のプロジェクト、人事の記録） | 機能や画面の存在が公開されている（契約と請求の設定、組織の設定） |
| ID や URL を推測して、存在を確かめられてしまう | 利用者が権限を申請・依頼すれば使える |

- 実際の応答（403 か 404 か）と情報公開のポリシーは、バックエンドで保証する。`pageAccessFromStatus` の `concealForbidden` は、バックエンドが 403 を返す API で、UI の表示だけを不存在にそろえる場合に使う。応答の時間や応答の内容の違いからも存在が推測できるため、UI だけで隠すことに頼らない。
- 「存在しない」の既定の文は、権限不足を不存在として扱う場合にも、そのまま使える文にしている（「削除された場合や、表示する権限がない場合も、このように表示されます」）。本当に存在しない場合と同じ文になり、表示の違いから存在を推測できない。

### 部分的な閲覧権限

- 制限の範囲を必要最小限にし、閲覧できる情報は表示し続ける。
- 存在を知らせてよい情報（メンバーの一覧）は、セクションを残して理由と申請を示す。存在を知らせてはならない情報は、セクションごと表示しない（見出しも置かない）。
- 次の経路からの漏えいも扱う。いずれもバックエンドが、閲覧できない対象を応答に含めない。

| 経路 | 扱い |
| --- | --- |
| 件数、集計値 | 閲覧できる対象だけで数える（プレビュー：閲覧者には 8 件のうち 6 件と示す） |
| 検索の候補、検索の結果 | 閲覧できる対象だけを返す。存在しない場合と同じ 0 件にする |
| 書き出し | 閲覧できる対象だけを書き出す。件数の表示も同じ |
| 通知 | 閲覧できない対象についての通知を送らない。権限を失った対象の通知は、本文を表示せず、移動先も示さない（[Notifications](notifications.md)） |
| エラーの文 | 対象の名前や内容を含めない（「この顧客を表示できなくなりました」） |

### 権限の申請

- 実際に利用できる解決の方法だけを示す：権限の申請、管理者への問い合わせ、自分で変更できる設定への移動、申請の状態の確認。申請の機能がない権限に、申請のボタンを形式的に置かない（プレビュー：「契約と請求を管理」は申請できないため、問い合わせ先だけを示す）。
- 必要な権限だけを申請できるようにする（ロール全体の変更を申請させない）。
- 申請、承認待ち、承認、却下の状態は、サーバーの申請の記録に基づいて示す。申請の結果が不明な場合は、申請の記録を取得し直して確かめ、再送しない。
- 二重申請を防ぐ。送信中は操作を受け付けず（状態の更新を待たずに判定する）、承認待ちの間は申請の操作を置かない。サーバーも、同じ権限の承認待ちの申請がある場合は、新しく作らずに既存の申請を返す。
- 承認されたら、権限の変更として反映する（再ログインを求めない）。

### 契約プランによる制限

- 契約プラン（Entitlement）とロールの権限（Authorization）を区別する。別の `kind` として持ち、文と解決の方法を変える。
- 有料の機能の存在を伝えることは許容する（「ビジネスプランで利用できます」）。プランの比較やアップグレードへの誘導を、操作のたびに繰り返さない。
- 契約を変更できる利用者には、契約プランを確かめる方法を示す。変更できない利用者には、問い合わせ先（管理者）を示す。
- 利用できる既存の機能を先に示す（プレビュー：組織の SSO がない場合、「現在は、多要素認証を必須にしてログインを保護しています」）。

### 利用中の権限変更

- 新しい権限を検知したら（製品の通知や定期的な確認で `revision` を変える）、`useAccess` が取得し直し、表示と操作を更新する。ページの再読み込みまで古い権限で操作させない。
- 取得し直す間（`refreshing`）は、前の権限を表示に使い（表示を揺らさない）、操作は許可しない（`decideAccess` が `unresolved` を返す）。取得し直しに失敗した場合は、知らせによる取得し直し（`revision` の変更）でも、同じ条件の再取得（`reload`）でも `stale` にし、同じスコープの前の権限で表示を保ち（ページを置き換えない）、操作は許可しない。「権限を再確認」で取得し直す。
- 権限が付与された場合は、安全に反映できる範囲で、再ログインを求めない。権限の昇格に再認証を求めるかは、製品の判断とする（例：管理者の権限の付与の直後の重要な操作）。
- 権限の変更は、常に置いた Live Region（`role="status"`）で知らせる。フォーカスを奪わない。
- 操作を押した後に権限が変わった場合も、サーバーが受け付けた時点の権限で判断し、その結果（拒否）を示す。

### 編集中の権限変更

| 変化 | 動作 |
| --- | --- |
| 編集の権限を失った | 保存を停止し、閲覧専用の表示にする。未保存の入力は、安全性と製品のポリシーが許す場合だけメモリに保持する（ポリシーで破棄も選べる） |
| 閲覧の権限も失った | 対象の内容を表示しない。入力は、ポリシーにかかわらず破棄する（入力に、閲覧できなくなった内容が含まれうるため）。理由は、対象の名前や内容を含まない文で伝える |
| 保存中に権限が変わった | サーバーの実際の結果を示す（拒否された場合は「保存されませんでした」）。結果が不明な場合は、取得し直して保存されたかを確かめる |
| 権限が戻った | 最新の権限（`ready`）と最新の内容を取得してから、編集を再開する。ほかの利用者の更新があった場合は、利用者が変更していない項目を最新の内容にし、変更した項目の入力を残して知らせる |
| フォーカスしていた入力欄が消えた | 変更を知らせる見出し（`tabIndex={-1}`）へフォーカスを移す（`useFocusRecovery`） |

### 権限の管理

- ロールの名前だけでなく、実際にできる操作を示す（Permission Matrix）。ロールの名前、説明、権限の一覧は製品のデータとして渡し、Registry で固定しない。RBAC、ABAC などの認可のモデルは製品が実装する。
- ロールの変更で影響の大きい権限（プレビュー：顧客の削除、メンバーの管理、契約と請求、組織の設定の変更、監査ログ）が増減する場合は、Alert Dialog で確認する。できるようになる操作とできなくなる操作を `diffPermissions` で求めて示す。影響の小さい変更（閲覧者 → メンバー）は確認せずに変更し、結果を Live Region で知らせる。
- 自分自身の行には、ロールを変更する操作を置かず、ロールを文字で示して理由を添える。
- 権限昇格（自分にない権限を含むロールの付与）、自分自身の権限の変更、最後の管理者の変更の検証は、バックエンドの責務とする。UI の制限に依存せず、拒否の応答（理由）をそのまま示す。プレビューの模擬のサーバーは、この順に検証して拒否する：操作する人の権限 → 対象 → 最後の管理者 → 自分自身 → 権限昇格。

## 状態管理

[System & Account の共通の状態管理](system-and-account.md)のうち、Permission States は Authorization、Entitlement、Scope を扱う。1 つの Boolean（`canEdit` など）や単一の error で持たない。

| 概念 | 持ち方 | 例 |
| --- | --- | --- |
| Authentication | 製品（Authentication の Pattern）。ログインしていない場合は、ページのアクセスの `unauthenticated` | 401 |
| Authorization | `AccessGrants.permissions`、`Restriction` の `authorization` | ロールの権限、個別に付与した権限 |
| Entitlement | `AccessGrants.features`、`Restriction` の `entitlement` | 契約プランの機能 |
| Scope | `useAccess` の `scopeKey`、`AccessGrants.scope` | `${userId}:${workspaceId}` |
| 権限の確定の状態 | `AccessSnapshot.status` | `loading`、`error`、`refreshing`、`stale`、`ready` |

### 表示と操作を分ける

- 表示（どのモードで描画するか）には `presentAction` と `resolveContentAccess` を使う。再確認中は前の権限で表示を決め、表示を揺らさない。
- 操作（押したときに実行するか）には `decideAccess` を使う。`ready` 以外では許可しない。Data Browsing の `canOperate` と同じ考え方である。
- 権限の取得中と取得の失敗は、許可として扱わない。表示の判断（`presentAction`）でも、管理の機能と存在を知らせない機能は、確定するまで表示しない（表示した後に消すと、存在を知らせ、表示も揺れるため）。

### スコープと古い結果

- `useAccess` は `useBrowseData` の `scopeKey` と要求ごとの番号を使う。スコープが変わったら、同じ描画から前のスコープの権限を返さない。A → B → A と戻った場合も、最初の A と B の応答を反映しない。`AbortSignal` に従わない取得の処理、アンマウントの後の応答も同じ。
- 応答の `scope` が要求したスコープと一致しない場合は、取得の失敗（`AccessScopeMismatchError`）とする。応答を無条件に信頼しない。
- 申請、保存、ロールの変更、操作の実行など、取得以外の非同期の処理は、`useScopeGuard`（`scope-guard.ts`）で、開始したときのスコープと最新の要求にだけ結果を反映する。
- アカウント、ワークスペース、認可の範囲が変わったら、前のデータ、入力、結果の文を引き継がない（プレビュー：結果の文をスコープと組で持ち、描画の時点で照合する）。

## アクセシビリティ

| 用途 | 指定 |
| --- | --- |
| 無効の操作 | `aria-disabled="true"`、フォーカスできる（`focusableWhenDisabled`）、理由を `aria-describedby` で関連付ける |
| 理由の文 | 常に表示する文。Tooltip だけにしない |
| 権限の変更の知らせ、申請の結果、保存の結果 | 常に置いた Live Region（`role="status"`）の中身を変える |
| 領域のエラー | `role="alert"`（Data States の `DataRegionError`） |
| ページのアクセスの状態 | 見出し（`role="heading"`、`aria-level`）で状態を示す。アイコンは飾り（`aria-hidden`） |
| Permission Matrix | `th scope="col"`、`th scope="row"`。記号（✓、—）は `aria-hidden` にし、「できる」「できない」の文を読み上げる |
| フォーカス | 権限の変更で操作が無効になっただけなら、フォーカスを動かさない。描画されなくなった場合だけ、変更を知らせる見出しへ移す |

- モバイルでも、理由と解決の方法を操作のすぐ後に表示する（Tooltip やホバーに依存しない）。
- 鍵のアイコンや色だけで状態を伝えない。Destructive の赤は、制限の表示に使わない（本当のエラーにだけ使う）。
- 動きを減らす設定（Reduced Motion）では、ボタンの処理中の回転（`motion-safe:animate-spin`）を止める。

UI 上の非表示と無効化は、実際の認可の代替ではない。次を共通の仕様とする。

- バックエンドで、アクセスと操作の認可を行う。操作を受け付けた時点の権限で判断する（画面を開いた時点の権限ではない）。
- 閲覧の権限がないデータを、クライアントへ送らない。UI で隠すだけにしない（プレビュー：閲覧できない顧客、メンバー、契約と請求は、模擬のサーバーが応答に含めない）。
- 未確定の権限で操作を許可しない。権限の取得の失敗を、許可として扱わない。
- URL、リクエスト、ワークスペースの ID を無条件に信頼しない。サーバーは、セッションの利用者が対象のワークスペースのメンバーであり、操作の権限を持つことを確かめる。クライアントも、応答のスコープが要求と一致することを確かめる。
- アカウント、ワークスペース、認可の範囲を変えたときに、以前のデータを引き継がない。
- 古い応答や非同期の処理によって、以前の権限を復元しない（`useAccess`、`useScopeGuard`）。
- 権限の変更の知らせは、変更を早く反映するための手段であり、認可の根拠にしない。知らせが届く前の操作も、サーバーが拒否する（プレビュー：ロールの管理の「通知が届く前の変更」）。
- 権限の申請の重複、権限昇格、自分自身の変更、最後の管理者の変更の検証は、バックエンドで行う。

## 製品側の責務

- 実際の認可（RBAC、ABAC など）と、ロール・権限・契約プランの定義。
- 権限の取得の API（`useAccess` の `fetcher`）。応答に、対象のスコープ（`scope`）を含める。
- 権限の変更の検知（通知、定期的な確認）と更新の頻度、セッションの管理、権限のキャッシュ。
- 操作ごとの性質の分類（業務の操作か管理の機能か、存在を知らせてよいか、申請できるか）。
- 理由の文、問い合わせ先、解決の方法（申請、設定への移動）の実装。
- 情報公開のポリシー（どの対象の権限不足を不存在として扱うか）と、件数、検索、書き出し、通知からの漏えいの防止。
- 未保存の入力を保持するかのポリシー。
- 権限の申請の重複の防止、権限昇格、自分自身の変更、最後の管理者の変更の検証。

## アンチパターン

| 避ける | 理由 | 代わりに |
| --- | --- | --- |
| すべての制限を「権限がありません」と示す | 障害、オフライン、契約プラン、前提の設定でも不要な申請をさせ、待てば使えることもわからない | 理由ごとに `kind` と文を分ける |
| 使えない機能をすべて非表示にする | 利用者が機能を探し続け、申請や問い合わせができない | 業務に関係する操作は、無効にして理由を示す |
| 使えない機能をすべて無効にして表示する | 業務に関係のない管理の機能で画面が複雑になり、存在を知らせてはならない機能も知らせる | 管理の機能と存在を知らせない機能は表示しない |
| 閲覧専用の画面で、すべての Input を Disabled にする | 文字が薄く読みにくい。編集できる画面と誤認する | 通常の文字で表示する |
| 理由を Tooltip だけに入れる | タッチで開かない。キーボードで操作に移動しても読めない場合がある | 操作のすぐ後に文で表示し、`aria-describedby` で関連付ける |
| 鍵のアイコンだけで制限を示す | 意味が伝わらない。理由も解決の方法もわからない | 文で示す |
| 権限の取得中に、操作を一時的に許可する | 権限が確定する前に、権限のない操作が送られる | `ready` 以外は許可しない |
| 権限の取得の失敗を「権限あり」として扱う | 取得できない場合に、すべての操作が許可される | `error` は許可しない。再確認を示す |
| ページの再読み込みまで古い権限で操作させる | 権限を外された利用者が操作を続けられる | 変更の知らせで取得し直し、その間は操作を止める |
| HTTP のステータスコードだけを示す（「403」） | 何が起きたか、次に何をすればよいかがわからない | 状態の文、移動先、解決の方法 |
| 機密の対象の権限不足を「権限がありません」と示す | 対象の存在を知らせる | 不存在と同じ応答と表示にする |
| 閲覧できない対象を件数や検索の候補に含める | 件数や候補から存在が推測できる | サーバーが閲覧できる対象だけで数え、返す |
| 申請の機能がない権限に「申請」を置く | 押しても解決しない | 問い合わせ先を示す |
| 申請の状態を画面の中だけで持つ | 再読み込みや別の端末で状態が失われ、二重に申請される | サーバーの記録から示す |
| ロールの名前だけを示す | 実際にできる操作がわからない | Permission Matrix |
| ロールを Registry で固定する | 製品ごとの認可のモデルに合わない | ロールと権限を製品のデータとして渡す |
| 権限昇格や最後の管理者の変更を UI だけで防ぐ | UI を経由しない要求で実行される | バックエンドで検証し、拒否の理由を示す |
| 閲覧の権限を失った後も、入力の内容や対象の名前を表示する | 閲覧できない情報を開示する | 内容と入力を破棄し、内容を含まない文で伝える |

## コードと資料の区分

| 区分 | 内容 |
| --- | --- |
| Registry のコード（`registry/patterns/`） | `access-decision.ts`（純粋な関数と型。`"use client"` なし、React と `@/` を import しない。Server Components とサーバーの処理から呼べる）：`decideAccess`、`presentAction`、`resolveContentAccess`、`pageAccessFromStatus`、`diffPermissions`、`restrictionText`、型（`Restriction`、`AccessSnapshot`、`AccessGrants`、`ActionPresentation`、`ContentAccess`）<br>`access.ts`（`"use client"`）：`useAccess`、`AccessScopeMismatchError`。`access-decision.ts` の関数と型を再 export する<br>`restricted-action.tsx`：`RestrictedAction`、`RestrictionNotice`、`useFocusRecovery`<br>`access-state.tsx`：`AccessState` |
| 組み合わせの例（プレビュー） | 閲覧専用の表示（`dl` と Read Only の Input）、Permission Matrix（Table）、ロールの変更の確認（Alert Dialog）、権限の申請（申請の記録の取得、二重申請の防止）、部分的な閲覧、契約プランの制限、編集中の権限変更（`permission-screens.tsx`） |
| 設計の資料だけ | 権限不足を不存在と同じに扱う判断基準、件数・検索・書き出し・通知からの漏えい、判断の順序 |
| 製品の責務 | 実際の認可、ロールと権限の定義、権限の変更の検知、セッション、情報公開のポリシー、バックエンドでの検証 |

Permission Matrix と権限の申請を Registry の部品にしなかった理由：Matrix は Table の組み合わせで足り、行と列の意味（権限、ロール、属性）が製品の認可のモデルで変わる。申請は、申請の単位、承認の流れ、申請の記録の API が製品ごとに異なる。どちらも、プレビューの例と資料にとどめた。

## 独自に判断した事項

| 事項 | 判断 | 理由 |
| --- | --- | --- |
| 判断の順序 | 未確定 → 契約プラン → 認可 → 再確認中 → 前提の設定 → 障害 → 接続 → 処理中 | 契約プランは申請では解決しない。構造的な理由を一時的な理由より先に示し、待てば使えると誤解させない |
| 契約プランと権限の両方が不足する場合 | 契約プランを理由にし、`entitlement.missing` に不足している権限も持つ。権限もない場合は、認可と同じく管理の機能を表示しない | 理由は 1 つだけ示すが、画面での扱い（表示するか）は、利用者の業務との関係で決めるため |
| 管理の機能と契約プラン | 権限を持つ利用者（管理者）には、契約プランで利用できない管理の機能も無効にして理由を示す | 業務に関係するかは利用者ごとに決まる。管理者にとって監査ログは業務の機能である |
| 権限の取得中の管理の機能 | 表示しない（業務の操作は無効にして「確認しています」） | 表示した後に消すと、存在を知らせ、表示も揺れる |
| 再確認中の表示 | 前の権限で表示を決め、操作だけを止める（`refreshing` と `stale` を `loading` と分ける） | 権限の変更の知らせのたびに表示が消えると、編集中の入力や読んでいる位置を失う |
| 知らせの後の取得の失敗 | `useBrowseData` は条件（`revision`）が変わった後の失敗を `error` にするが、`useAccess` は同じスコープの前の権限があれば `stale` にする（`browse-data.ts` は変更しない） | 取得の失敗のたびにページ全体を「権限を確認できませんでした」に置き換えると、閲覧できていた内容と入力を失う。操作は `stale` でも許可しない |
| 処理中の状態とスコープ | 操作の実行、申請、ロールの変更、保存の処理中の状態を、開始したときのスコープの世代（`useScopeGuard` の ticket）と組で持ち、現在のスコープで始めた処理だけを処理中として示す | 処理中にスコープを切り替えると、応答を反映しない処理の「処理中」が残り、別のスコープ（A → B → A で戻った A を含む）の操作が止まったままになる（Data Browsing の `useBulkAction` と同じ考え方） |
| 応答のスコープの照合 | `useAccess` は、応答の `scope` が要求と異なる場合に取得の失敗とする | URL やリクエストの ID を無条件に信頼しない。サーバーやキャッシュの誤りで別のスコープの権限を使わない |
| 閲覧の権限を失ったときの入力 | ポリシーにかかわらず破棄する | 入力に、閲覧できなくなった内容が含まれうる |
| 権限が戻ったときの入力 | 利用者が変更していない項目は最新の内容にし、変更した項目は入力を残して知らせる | 最新の内容を確かめずに、古い内容の上で保存させない。入力は失わない |
| 自分自身の行 | ロールの Select を Disabled にせず、ロールを文字で示して理由を添える | Disabled の Select はフォーカスできず、キーボードで理由に届きにくい |
| 影響の大きいロールの変更 | 製品が渡す `sensitive` の権限が増減する場合だけ確認する | すべての変更を確認すると、確認が形式的になる |
| 「存在しない」の既定の文 | 権限不足の可能性も含む文にする | 権限不足を不存在として扱う場合に、表示の違いから存在を推測させない |
| 権限の変更の知らせ | 確定した権限が変わったときだけ、Live Region で知らせる | 再取得のたびに読み上げない |
| 権限の申請の結果が不明 | 再送せず、申請の記録を取得し直して示す | 申請が作られている場合に、重複して作らない |

## 統合時に確認する事項

- Forms & Workflows の Confirmation が統合されたら、ロールの変更の確認（現在は Alert Dialog を直接使用）を Confirmation の Pattern に置き換える。
- Forms & Workflows の Unsaved Changes が統合されたら、編集中の権限変更の「入力の保持・破棄」と、移動の際の未保存の確認（`DiscardAlert`）の関係をそろえる。
- Forms & Workflows の Create & Edit、Form Layout が統合されたら、閲覧専用の表示と編集の画面の配置を、その Pattern に合わせる。
- Data Analysis が統合されたら、集計値と Chart での「閲覧できない対象を含めない」を、その Pattern の資料にも記載する。
- 統合の検証画面（`account-app.tsx`）では、Authentication のセッション、Settings の組織の設定、Notifications の通知（閲覧できない対象の通知）、System States の障害の表示と、同じ `PermissionScope` と模擬のサーバーの状態を共有するかを決める。
