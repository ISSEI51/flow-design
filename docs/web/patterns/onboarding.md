# Onboarding

利用者が最初の価値を体験するまでの時間を短くする。機能の説明より、実際の利用を優先し、必要な知識は使うときに示す。

状態：v0.1 確定候補（設計と実装の方針は承認済み。Patterns Integration Review の前） ・ 実装：[`registry/patterns/onboarding.ts`](../../../registry/patterns/onboarding.ts)、[`registry/patterns/getting-started.tsx`](../../../registry/patterns/getting-started.tsx)、[`registry/patterns/contextual-help.tsx`](../../../registry/patterns/contextual-help.tsx) ・ 全体：[System & Account](system-and-account.md)

## 目的

認証の後、利用者が迷わずに製品を使い始め、最初の価値（例：最初の顧客を登録し、一覧で確かめる）に早く届くようにする（原則 01、07）。自明な機能を 1 つずつ説明せず（原則 04）、利用開始に必要のない設定や質問で利用を妨げない。一方で、利用を続けるために必要な作業（支払い方法など）は、案内を閉じても見えなくしない（原則 08）。

## 使用条件

| 部品・方式 | 使う場合 | 使わない場合 |
| --- | --- | --- |
| 独立した初回の画面 | 組織の作成、招待の承諾、利用開始の前に必要な設定（組織のポリシーで必須の多要素認証など） | 歓迎の文と「始める」だけの画面 |
| 組織の作成（複数の手順） | 意味のある手順が複数ある場合 | 組織名だけで作成できる場合（1 画面にする） |
| Getting Started Checklist | 製品の利用につながる初期作業が複数（目安 3〜5 件）ある場合 | 作業が 1 件以下の場合（`presentation` が `none`）。招待されたメンバーで、組織の作業が完了している場合 |
| 初回利用の Empty State | 一覧などにデータがまだない場合 | 検索結果 0件、取得失敗（それぞれの表示にする） |
| Contextual Help | その操作を使える状態で、知っておくと迷わずに済む短い情報がある場合 | 見ればわかる操作の説明 |
| Product Tour | 複雑な専門機能で、説明によって学習の負荷が下がる場合だけ検討する | 標準では使わない。自明なボタンや検索欄を順番に説明しない |
| サンプルデータ | 価値の体験に実際のデータの構造が必要で、利用者が明示的に選んだ場合 | 自動で入れる。実際のデータに混ぜる |

### 初期設定の 3 種類

| 種類 | 例 | 求める場所 |
| --- | --- | --- |
| 利用開始の前に必要な設定 | 組織名（組織を作成する場合）、組織のポリシーで必須の多要素認証 | 初回の画面。これがないと利用を始められないものだけ |
| 利用開始の後でも可能な設定 | 表示言語、タイムゾーン、通知、プロフィールの写真 | 求めない。合理的な初期値（組織の標準、端末の設定）で始め、設定の画面で変える |
| 特定の機能を使うときに必要な設定 | 支払い方法（試用期間の終了時）、外部のカレンダーとの連携 | その機能を使う画面。Checklist に作業として示してもよい |

#### 必須の設定が完了していない場合の操作の制限

- 利用開始の前に必要な設定（組織のポリシーで必須の多要素認証など）が完了していない間は、`resolveFirstScreen` が `required-setup` を返し、製品の利用画面へ移らない。製品のルーターは、認証の直後だけでなく、製品の画面へ移るたび（直接の URL、ブックマーク、通知からの移動を含む）に判定し直す。バックエンドも要求ごとに要件を確かめる（画面の制御は認可ではない）。
- 利用を続けるための必須の作業（試用期間の終了後の支払い方法など）は、`deriveChecklist` の `requirementsMet`（または `deriveRequirements` の `met`）で判定する。Checklist の表示（非表示、`presentation: "none"`）、権限による作業の除外で、要件を達成したとして扱わない。どの時点でどの機能を制限するか（試用期間の終了日など）は製品が決める。プレビューは試用期間の終了を模擬しないため、機能の制限そのものは示していない（要件が未達成であることの表示だけを示す）。

#### 任意の設定をスキップした場合の初期値

| 設定 | スキップした場合、または変更しなかった場合 | 後から行う場所 |
| --- | --- | --- |
| 使い方（チーム、自分だけ） | チームで使う（招待の手順を含む） | 組織の作成の 1 番目の手順 |
| メンバーの招待 | 招待しない（入力していた宛先も送信しない）。Checklist の「メンバーを招待する」は未完了のまま残る | メンバーの画面 |
| 顧客データの始め方 | 空の状態から始める（サンプルデータを作らない。サンプルは利用者が明示的に選んだ場合だけ） | 初回利用の Empty State の「サンプルデータで試す」 |
| 表示言語、タイムゾーン | 組織の標準（招待されたメンバー）、または端末の設定 | 個人の設定（[settings.md](settings.md)） |

- 利用目的、業種、組織の規模などの質問は、実際の体験を変える場合だけ求める（例：「チームで使う／自分だけで使う」で招待の手順を省く）。
- マーケティングの目的の質問（製品を知ったきっかけなど）を、必須の設定に混ぜない。尋ねる場合は任意にし、利用開始の後に回す。

## バリエーション

| 利用者 | 初回の画面 | Checklist | Empty State |
| --- | --- | --- | --- |
| 新規登録して組織を作成した管理者 | 組織の作成 | 組織単位とアカウント単位の作業（5 件） | 登録、取り込み、サンプル |
| 既存の組織に招待されたメンバー | 招待の承諾 | 組織で完了済みの作業を除く。権限のない作業を除く（例：メンバーは招待と支払いを除く） | 組織にデータがあれば一覧を表示する |
| 招待された閲覧者 | 招待の承諾 | 作業が 1 件以下のため使わない | 登録の操作を置かない |
| 所属する組織がある利用者 | 利用画面へ直接移る | 完了または非表示なら表示しない | 通常の表示 |

## 動作

### 初回の画面

- 認証の後は、原則として製品の利用画面（最初の価値を体験する画面）へ直接移る。認証の後の戻り先（直前のページ）の扱いは [authentication.md](authentication.md) に従う。
- 独立した画面は、組織の作成、招待の承諾、利用開始の前に必要な設定のように、利用者が判断や入力をする意味がある場合だけ挟む。
- 歓迎するだけの画面、作成の後の成功の画面を挟まない。

### 組織の作成

- 位置は簡易の `Stepper`（`layout="compact"`、`currentLabel="hidden"`）の「ステップ 2 / 3」で示し、手順の名前は直後の見出し（「メンバーを招待」）で示す（同じ名前を続けて示さない。支援技術には、Stepper の番号の後に「（現在のステップ：メンバーを招待（任意））」を伝える）。必須と任意は、見出しの直後の文（「必須の手順です。」「任意の手順です。スキップしても、あとで設定できます。」）と、手順の一覧の名前（「メンバーを招待（任意）」）で示す。必須の項目は組織名だけにする。
- 「次へ」は、現在の手順の必須の項目と検証が完了するまで押せない（Focusable Disabled。`aria-describedby` で「あと 1 項目を入力すると次へ進めます」などの理由を示す）。1 行の入力欄の Enter で次へを求めた場合は、その手順の項目のエラーを示し、最初の問題の項目へフォーカスを移す。メールアドレスの形式の誤りは、入力欄からフォーカスを外すと示す。
- 完了した手順へは、簡易の Stepper の「すべての手順」から直接戻れる。
- 任意の手順は「スキップ」で飛ばせる。入力がないまま「次へ」を押した場合もスキップとして扱う。スキップした作業（メンバーの招待）は、Checklist に作業として残る。
- 「戻る」で前の手順に戻っても、入力は残る。
- 途中の入力は、手順を移るたびに製品が保存する（プレビューでは模擬のサーバー）。画面を閉じた、再読み込みした、別の端末で開いた場合は、続きの手順から再開し、「前回の入力の続きから再開しています」と示す。最初から入力し直すこともできる（保存した途中の入力も削除するため、`DiscardChangesAlert` で確かめる。作成の結果が不明な間、作成中、確認中、途中の入力の保存中は押せない。新しい作成の要求の ID で、同じ組織を二重に作成しないため）。
- 前回の手順の保存の後に入力した内容（手順を移る前の入力）と、結果が不明な作成は、Unsaved Changes（`useUnsavedChanges`）で守る。プレビューの「画面を閉じる（中断）」は `confirmNavigation` で確かめ、再読み込みとタブを閉じる操作は `beforeunload` で確かめる。途中の入力の保存中に閉じた場合は、保存が終わるまで待つ。作成の要求の実行中は確認の対象にしない（作成の要求の ID で二重に作成されず、閉じた後の応答は反映しない。作成されなかった場合は保存した途中の入力から再開できる）。
- 分岐で不要になった手順（「自分だけで使う」を選んだ場合の招待）は、手順の数から除き、入力していた内容を送信しない。
- 手順を移ったら、その手順の見出しにフォーカスを移す。
- 作成の要求は二重に送らない（実行中は受け付けない。要求の ID を付け、同じ ID は 1 回だけ処理する）。
- 作成に失敗した場合は、入力を残して Alert（`role="alert"`）で示す。結果が不明な場合（通信が途中で切れた）は、もう一度作成するボタンを止め、「作成されたかを確認する」で確かめてから、作成されていれば利用画面へ、作成されていなければ再び作成できるようにする。
- 作成した後は、成功の画面を挟まずに利用画面へ移る。「サンプルデータで試す」を選んだ場合は、サンプルの領域を表示する。

### Getting Started Checklist

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="../../diagrams/checklist-states-dark.svg">

</picture>

- 完了は、製品が渡す実際の作業結果（完了した作業の ID）だけで判定する。例：顧客を実際に登録したら「最初の顧客を登録する」が完了する。作業のボタン（「顧客を登録」「支払いの画面へ」）は作業の画面へ移る操作であり、押しただけでは完了にしない。登録の Sheet を開いて閉じた場合も完了にしない。
- 作業のボタンの名前は、押した結果（移る先や開く画面）がわかる名前にする（`actionLabel`）。
- 完了した件数（「5 件中 2 件完了」）と進捗（Progress）を示す。状態は「完了」の文字と、支援技術向けの「完了：」「未完了：」でも伝え、色とアイコンだけで伝えない。
- 折りたたみ（件数と進捗だけ）、非表示、再表示ができる。再表示の入口は、非表示にしても場所の変わらない所（画面の上部、ヘルプのメニューなど）に置く。
- 非表示は表示の状態であり、完了ではない。非表示にしても `progress` と `requirementsMet` は変わらない。必須の作業（支払い方法）が残っている場合は、非表示にした後も Alert で示し続ける。
- 必須の条件（`requirementsMet`、`requirements`）は、Checklist の表示の対象（`items`）とは別の値で、すべての作業の定義と実際の作業結果から判定する。権限のない作業を Checklist から除いても、必須の条件は達成にならない。例：メンバーには「支払い方法を登録する」を表示しないが、支払い方法が未登録の間は `requirementsMet` が `false` のまま。この利用者が行える残りの必須の作業は `outstandingRequired`、権限がなく行えないものは `outstandingRequiredWithoutPermission` に入る。プレビューでは、権限のない利用者に「この作業は、権限のある組織の管理者が行います」と示す（操作のボタンは置かない）。権限のない利用者に示すかどうかと文は、製品のポリシー（情報の機密性）で決める。示さない場合も、要件の判定は変えない。
- 対象の作業が 0 件の場合（権限と利用者の種類ですべて除いた）は、`progress: "none"`、`presentation: "none"` とし、「完了しました」と示さない（下の「独自に判断した事項」）。
- 役割や権限が変わったら、同じ作業結果から対象の作業を導き直す（`permissions` を変えて `deriveChecklist` を呼ぶ）。完了の件数は、表示する作業の中だけで数える。プレビューでは `scopeKey` に権限を含めるため、権限が変わると取得をやり直し、前の権限の Checklist と完了の読み上げを引き継がない。
- 完了は記憶せず、渡された作業結果から毎回導く。完了した作業が後から未完了になった場合（顧客をすべて削除した、支払い方法を削除した）、結果から ID が消えれば未完了に戻り、すべて完了の表示（`completed`）から、保存されている表示の状態（展開、折りたたみ）に戻る。すべて完了の後に閉じていた（`hidden`）場合は非表示のままだが、必須の作業が残れば Alert で示す。作業結果が変わったときに取得し直すこと（通知、画面の再表示など）は製品の責務である。
- すべて完了した場合は、「利用開始の準備が完了しました」と短く示し、「閉じる」で非表示にできる。閉じた後は表示しない。
- 権限のない作業は表示しない（作業の `permission`）。招待されたメンバー（`audience: "invited"`）には、組織で完了済みの作業を表示しない（設定済みの項目を再設定させない）。
- アカウント単位の作業（プロフィールの写真）と組織単位の作業（顧客、取り込み、招待、支払い）を分ける。組織単位の作業は、誰が行っても組織で完了になる。アカウント単位の作業は、ほかの組織でも完了のまま示す。
- 同じ利用者が別の組織へ切り替えた場合は、アカウント単位の結果を引き継ぎ、組織単位の結果と表示の状態（利用者 × 組織で保存）は切り替えた先の組織のものを使う。切り替えの間に、前の組織の Checklist を表示しない（`scopeKey` に組織を含める）。
- 作業が完了したら、Checklist の中に常に置いた読み上げの領域で「「最初の顧客を登録する」が完了しました。5 件中 2 件が完了しています」と伝える。最初の表示と、利用者・組織の切り替え（`scopeKey`）では読み上げない。

### 初回利用の Empty State

- 既存の `Empty` を使い、何ができるか（「顧客を登録すると、商談と契約の記録を始められます」）、最初に何をするか、どこから操作するか（「ページの上部の「顧客を登録」から」）を短く伝える。
- Page Header に同じ操作（「顧客を登録」）がある場合は、Empty に同じボタンを置かない。ほかの始め方（「CSV から取り込む」「サンプルデータで試す」）だけを置く。
- 未登録、検索結果 0件、取得失敗を区別する（Data Browsing の `getBrowseViewState`）。検索結果 0件は「条件に一致する顧客はいません」と「検索をクリア」、取得失敗は `DataRegionError` と再試行にする。取得失敗を初回利用の Empty にしない。
- データがまだない間は、検索欄を置かない（検索する対象がない）。
- 登録の権限がない利用者には、登録の操作を置かず、「登録されると、ここに表示されます」と示す。

### Product Tour

- 強制的な Tour は標準にしない。初回のログインで自動的に始まり、終わるまで操作できない Tour を作らない。
- 複雑な専門機能など、説明によって学習の負荷が下がる場合だけ検討する。利用者が自分で開始し、途中で終了し、必要に応じて続きから再開できるようにする。
- 汎用の Product Tour の仕組みは、このリリースでは提供しない（14 章の対象外）。

### Contextual Help

- 関係する操作の近くに、画面の流れの中に置く（`role="note"`）。入力欄やボタンを覆わない（Popover やモーダルにしない）。表示したときにフォーカスを奪わない。
- その操作を使える状態のときだけ表示する（例：顧客の検索の案内は、顧客が 1 件以上あり、検索語が空のときだけ）。
- 閉じるボタン（「この案内を閉じる」）を置く。閉じたときにフォーカスが案内の中にあった場合は、関係する入力欄に移す（`focusAfterDismiss`）。
- 閉じた状態はアカウントごとに保存し、再読み込みや別の端末でも表示しない（製品の責務）。保存した状態の取得が終わるまでは表示しない（閉じた案内が一瞬表示されない）。保存に失敗しても、その画面の間は表示しない。
- 閉じた状態のスコープはアカウント（利用者）とする。同じ利用者が別の組織へ切り替えても、役割が変わっても、閉じた案内を再び表示しない。別の利用者には引き継がない。理由：案内は製品の操作の説明であり、組織のデータに依存しないため。組織や役割で内容が変わる案内は、別の ID にする（例：メンバーの画面の `members-role-tasks`）。組織ごとに表示し直す必要がある案内を作る場合は、製品が利用者 × 組織で保存する。
- 重要な情報を一度だけの案内に置かない。項目の説明（`FieldDescription`）やヘルプのページにも置く。

### サンプルデータ

- 利用者が明示的に選んだ場合だけ用意する（組織の作成の最後の手順、初回利用の Empty State の「サンプルデータで試す」）。
- サンプルを表示している間は、画面の上部に「サンプルデータを表示しています」を常に示し、行にも「サンプル」と示す。件数も「サンプル 4 件」と区別する。
- 実際のデータと別の領域に保存する。サンプルへの登録は、実際の顧客の件数、利用開始の準備（Checklist の完了）、集計、請求、通知、外部への送信の対象にしない。
- 「実際のデータに戻る」と「サンプルを削除」を、サンプルの表示の上部に常に置く。実際のデータの表示からも「サンプルを表示」で戻れる。
- 見た目のラベルだけでは分離にならない。保存の領域、検索、集計、通知、外部への送信、請求の処理で分けることは製品の責務である。プレビューでは、模擬のサーバーの中でサンプルの領域（`sample`）を分け、サンプルからの操作が実際のデータに伝わらないことを検品している。
- 型でも分ける。プレビューの模擬のサーバーでは、実際の顧客（`RealCustomer`、`sample: false`）とサンプルの顧客（`SampleCustomer`、`sample: true`）を別の型にし、実際の領域、請求の対象の件数（`getUsage`、実際の領域だけを数える）、外部への送信の記録は `RealCustomer` だけを受け付ける。サンプルの顧客を実際の顧客として渡すと、型の検査で失敗する（単体の検品の `@ts-expect-error`）。製品では、サンプルの記録を請求、外部への送信（メール、Webhook、連携先）、正式な集計に渡す関数の引数の型と、バックエンドの処理の対象の条件の両方で除く。
- サンプルを表示している間も、ほかの作業の画面（取り込み、メンバー、支払い、プロフィール）は実際のデータを対象にする。作業の画面から顧客の画面へ戻ると、実際のデータを表示する。プレビューの支払いの画面は、請求の対象の顧客の件数（サンプルを含めない）を示す。

### 結果が不明な操作

作業の画面の変更の操作（顧客の登録、取り込み、招待、支払い方法、プロフィールの写真、サンプルの用意と削除、招待の承諾）は、組織の作成と同じ規則で扱う（[system-and-account.md](system-and-account.md) の共通の状態管理と安全性）。

- 実行中は同じ操作を受け付けない（ボタンは Loading）。
- 操作ごとに要求の ID を付ける。バックエンドは同じ ID の要求を 1 回だけ処理する（冪等）。プレビューの模擬のサーバーも、要求の ID で 1 回だけ処理する。
- 確定した失敗（サーバーが拒否した。プレビューの `MockRequestError`）だけを失敗として、もう一度実行できる状態にする。それ以外の例外（通信の例外、予期しない例外）は、サーバーで処理が終わっている可能性があるため、結果が不明として扱う（Forms & Workflows の `FormSaveError` と同じ既定値）。組織の作成と表示の状態の保存も同じ規則にした。
- 結果が不明な場合（応答が届かなかった）は、成功として表示しない。同じ操作のボタンの代わりに「処理されたかを確認する」を置き、もう一度実行させない（Enter で送信した場合も確認になる）。あわせて作業結果を取得し直し、実際の状態を表示する。
- 確認では要求の ID を照会する。処理されていれば成功として扱い（「処理されていました。3 件を取り込みました。」）、処理されていなければ、もう一度実行できるようにする（「処理されていませんでした。もう一度行えます。」）。確認にも失敗した場合は、確認の操作を残す。
- 顧客の登録の Sheet では、結果が不明な場合も Sheet を閉じず、Sheet の中で結果と確認の操作を示す。

### 同時に示す案内

- 同時に表示する案内は 1 つにする（`pickGuidance`）。Empty State を表示している領域には、Contextual Help を出さない。
- Checklist は通常の操作の領域を圧迫しないよう、折りたたみと非表示を提供し、狭い領域では作業の補足の説明を省く。

## アンチパターン

| 避ける | 理由 | 代わりに |
| --- | --- | --- |
| 認証の後に歓迎の画面を挟む | 押す以外にすることがなく、利用までの手順が増える | 利用画面へ直接移る |
| 作成の後に「作成しました」の画面を挟む | 利用までの手順が増える | すぐに利用画面へ移る |
| マーケティングの質問を必須にする | 利用開始を妨げる | 任意にし、利用開始の後に回す |
| 後から設定できるものを最初に求める | 最初の価値体験が遅れる | 初期値で始め、設定の画面で変える |
| Checklist の項目をチェックで完了にする | 作業をしていなくても完了になる | 実際の作業結果で判定する |
| 非表示にしたことを要件の達成として扱う | 必須の作業が残ったまま見えなくなる | 進捗と要件を表示と別に持ち、残った必須の作業を示す |
| 権限のない作業を Checklist に出す | 押しても行えない | 権限で絞り込む |
| 招待されたメンバーに組織の設定を再び求める | 設定済みのことを繰り返させる | 組織で完了済みの作業を示さない |
| Page Header と Empty State に同じ操作を置く | どちらを押すか迷う | 操作は 1 か所にし、Empty では場所を示す |
| 初回利用の Empty と検索結果 0件を同じ表示にする | 次にすべき操作が異なる | `getBrowseViewState` で区別する |
| 自明なボタンを順番に説明する Tour | 見ればわかることを説明し、操作を止める | 必要な場所の短い Contextual Help |
| 閉じた案内を次の訪問で再び表示する | 繰り返しが負担になり、案内を読まなくなる | 閉じた状態をアカウントごとに保存する |
| サンプルを実際のデータに混ぜる | 集計、請求、送信の対象になる | 別の領域に保存し、常に識別できるようにする |
| 案内を複数同時に表示する | どれを読むか迷い、操作の領域が狭くなる | 1 つにする |
| 結果が不明な操作を、そのままもう一度実行できる | 取り込みや招待が重複する | 確認の操作だけを置き、要求の ID を照会する。バックエンドは要求の ID で冪等にする |
| 演出のための待ち時間やアニメーション | 不要な待ち時間 | すぐに利用画面を表示する |

## 状態管理

| 状態 | 意味 | 持つ値 |
| --- | --- | --- |
| 未開始 | 作業や手順を、まだ 1 つも始めていない（保存した途中の入力がない） | `progress: "not-started"`、`getSetupStatus` の `not-started` |
| 進行中 | 一部が完了している、または途中の入力を保存して手順の画面を操作している | `in-progress` |
| 中断 | 途中の入力が保存されていて、手順の画面を閉じた（再読み込み、別の端末を含む）。続きから再開できる | `interrupted` |
| スキップ | 任意の手順を行わないことにした。完了ではない（Checklist に作業として残る） | 製品が保存する手順の ID（プレビューの `SetupDraft.skipped`）、`getSetupStatus` の `skipped`（任意の設定の全体を行わないことにした場合） |
| 非表示 | 利用者が Checklist を非表示にした。表示の状態であり、進捗は変わらない | `visibility: "hidden"` |
| 完了 | 実際の作業結果で、すべての作業が完了した。組織の作成では、作成した | `progress: "completed"`、`completed` |

- 進捗（`progress`、`requirementsMet`）と表示（`visibility`、`presentation`）を別の値で持つ。1 つの Boolean（`onboardingDone` など）にまとめない。
- アカウント単位の進捗（`results.account`）と組織単位の進捗（`results.workspace`）を分けて渡す。`deriveChecklist` は、作業の `scope` と異なる範囲の結果を完了として数えない。
- 表示の状態、スキップ、途中の入力、閉じた案内は製品が保存する（サーバーなど）。ページの再読み込みや別の端末で、初期状態に戻さない。Registry の部品は状態を保存しない（LocalStorage、URL、Cookie に依存しない）。
- 利用者、組織、権限が変わったら、前の利用者の Checklist を 1 回の描画でも表示しない。プレビューでは、取得に `useBrowseData`（`scopeKey` に利用者、組織、権限）、表示の状態の保存に `useScopeGuard` を使い、A → B → A と切り替えても、最後の A の結果だけを反映する。
- 古い画面からの操作の開始を防ぐ。顧客の登録の Sheet は、開いたときに `capture()` した Snapshot を持ち、`isCurrent(snapshot)` が `false` になったら（利用者、組織、権限、データの領域の変更。A → B → A を含む）閉じた状態として扱う。登録は `beginIfCurrent(snapshot, "add")` で始め、Snapshot が現在と一致しない場合は始めない（前のスコープで入力した会社名を、新しいスコープで登録しない）。
- 処理の終わりに `release(ticket)` を呼び、処理のキーの記録を消す（最後の `isLatest` の照合の後）。実行中の判定は、描画の中で記録を消さず、記録した Ticket の `isLatest` で行う（前の世代の Ticket は最新ではないため、新しいスコープの操作を妨げない。破棄された描画や StrictMode の 2 回目の描画で、表示中のスコープの実行中の記録を消さない）。
- 画面に示す実行中の状態（ボタンの Loading）と、保存中の表示の状態（Checklist の表示・非表示）も、処理を始めたときの Ticket と組で持ち、`isSameScope(ticket)` が `true` のものだけを使う。処理が終わったら、スコープにかかわらず、その Ticket の記録を外す。v0.1 の最終調整までは `scopeKey` の文字列と組で持っていたため、A → B → A の最初の A で始めた操作が、戻った A で「実行中」のまま残った（その応答は最初の A の世代のため反映せず、記録を消す処理にも届かなかった）。
- 前のスコープの描画の関数から呼ばれた場合（`useScopeGuard` の無効な Ticket）は、要求を送らない（プレビューの `useActions` と表示の状態の保存）。
- 保存の要求（表示の状態、閉じた案内、途中の入力、作成）は、画面を閉じても中止しない（中止しても、サーバーで処理されることがあるため）。結果は、開始したときのスコープの最新の要求にだけ反映し、アンマウントの後は反映しない。
- 表示の状態の保存に失敗した場合は、保存されている状態に戻して知らせる。結果が不明な場合は、保存されている状態を取得し直す。取得し直した結果が届くまでは「表示の状態を保存できたかを確認しています。」と示し、届いた後に「表示の状態を保存できたかを確認できませんでした。保存されている状態を表示しています。」と示す（取得も失敗した場合は、保存されている状態も取得できなかったと示す）。以前は、取得の応答の前から「保存されている状態を表示しています」と示していた（ONB-4）。
- 作業の変更の操作の結果が不明な場合は、操作ごとに「確認が必要」（要求の ID）を持ち、確認が終わるまで同じ操作を実行しない（プレビューの `useActions`）。確認が必要な状態も、開始したときのスコープの中だけで持つ。

### deriveChecklist の値

| 値 | 意味 |
| --- | --- |
| `items` | 表示する作業（権限と利用者の種類で絞り込んだもの）。`done`、`required`、`scope` を持つ |
| `doneCount`、`total` | 完了した件数と、表示する作業の件数 |
| `progress` | `not-started`、`in-progress`、`completed` |
| `visibility` | 利用者が選んだ表示（`expanded`、`collapsed`、`hidden`） |
| `presentation` | 実際に表示する形（`none`、`hidden`、`completed`、`expanded`、`collapsed`）。上の図の表の順に判定する |
| `progress` の `none` | 対象の作業が 0 件。完了（`completed`）ではない |
| `requirementsMet`、`requirements` | 必須の作業がすべて完了したか（`requirements.met`）と、完了していない必須の作業の一覧（`requirements.outstanding`、権限のないものを含む）。権限、利用者の種類、表示の状態で変わらない。`deriveRequirements` で Checklist なしでも求められる |
| `outstandingRequired` | 完了していない必須の作業のうち、この利用者が行えるもの（Checklist に表示する作業） |
| `outstandingRequiredWithoutPermission` | 完了していない必須の作業のうち、この利用者に権限がないもの（`id`、`title`、`scope`、`permission`）。Checklist に表示しない |

## 評価指標

計測の仕組み（イベントの収集、分析の基盤）は、このリリースでは提供しない。製品が最初の価値体験を定義し、次の判断基準で評価する。チュートリアルや Tour の完了率だけで品質を判断しない（完了しても価値を体験していない場合がある）。

| 指標 | 定義 | 判断の基準 |
| --- | --- | --- |
| Time to First Value | 登録から、製品が定義した最初の価値体験までの時間 | 短いほどよい。長い場合は、利用開始の前の設定と質問、待ち時間を見直す |
| Activation Rate | 登録した利用者のうち、最初の価値体験に達した割合 | Checklist の完了ではなく、価値体験の到達で数える |
| Setup Completion Rate | 必須の初期設定を完了した割合 | 任意の手順のスキップを失敗に数えない |
| Step Drop-off | 手順ごとの離脱の割合 | 離脱の多い手順は、必須か、後に回せるか、質問が必要かを見直す |
| Onboarding 後の継続率 | 最初の価値体験の後も使い続けている割合（例：1 週間後、4 週間後） | Onboarding の変更の効果は、継続率で確かめる |

## アクセシビリティ

| 用途 | 指定 |
| --- | --- |
| Checklist | `<section aria-labelledby>`（見出し）。折りたたみのボタンは `aria-expanded` と `aria-controls`。作業の状態は「完了：」「未完了：」（支援技術向け）と「完了」の文字 |
| 進捗 | Progress（`aria-valuetext` に「5 件中 2 件完了」）。件数は文字でも示す |
| 作業の完了 | Checklist の中に常に置いた `role="status"`。新しく完了した作業だけを読み上げる。最初の表示と切り替えでは読み上げない |
| 画面の移動 | プレビューの製品の画面では、`role="status"` で「支払いの画面を表示しています」と伝える。フォーカスは押したボタンに残す |
| 組織の作成 | 手順を移ったら、手順の見出し（`tabIndex={-1}`）にフォーカスを移す。失敗と結果の不明は `role="alert"` |
| Contextual Help | `role="note"`。閉じるボタンは「この案内を閉じる」。閉じた後のフォーカスは関係する入力欄へ |
| 非表示と再表示 | 非表示にしたら再表示の入口へ、再表示したら Checklist（`tabIndex={-1}`）へフォーカスを移す（`<body>` に落とさない） |

- キーボード、タッチ、スクリーンリーダーで、すべての操作ができる。ボタンの高さは 40px 以上（`size="sm"`）、主要な操作は 48px。
- 状態の変化でフォーカスを奪わない。Checklist の完了の読み上げは polite。
- 動きを減らす設定では、Sheet の移動などの動き（既存の Components の `motion-safe:`）を止める。Onboarding のための待ち時間やアニメーションは置かない。
- 実機（iOS Safari、Android）とスクリーンリーダー（VoiceOver、NVDA）による確認は、まだ行っていない。

## セキュリティ上の注意

- 権限のない作業を Checklist に表示しないのは表示の制御であり、認可ではない。作業の画面と API で、バックエンドが権限を確かめる。
- 招待の承諾では、招待のトークンの検証、期限、招待された宛先と認証した利用者の一致を、バックエンドで確かめる（プレビューは模擬の招待）。
- 招待のメールアドレスなどの途中の入力は、個人情報を含む。保存する場合はアカウントに結び付けてサーバーに保存し、URL、LocalStorage、ログに残さない。
- 利用者や組織を切り替えたら、前の利用者の進捗、途中の入力、閉じた案内を表示しない（`scopeKey`）。
- サンプルの領域のデータを、外部への送信、請求、正式な集計の処理に渡さない（製品のバックエンドで分ける）。
- 組織の作成、顧客の登録、取り込み、招待などの変更の要求には要求の ID を付け、同じ ID を 1 回だけ処理する（冪等性。バックエンド）。結果が不明な要求を、確認せずに新しい ID で送り直さない。

## 製品側の責務

- 状態の永続化：Checklist の表示の状態（利用者 × 組織）、閉じた案内（アカウント）、組織の作成の途中の入力とスキップ（アカウント）。
- 実際の作業結果の取得（顧客の件数、取り込み、招待、支払い方法、プロフィールの写真）と、`results.account` と `results.workspace` への振り分け。サンプルを含めない。
- 利用開始の前に必要な設定の判定（組織のポリシー、規約など）と、`resolveFirstScreen` の結果に応じたルーティング。
- 最初の価値体験の定義と計測（評価指標）。
- 必須の作業が残る場合の機能の制限（試用期間の終了時など）と、その案内。判定には `requirementsMet` を使い、Checklist の表示や権限による除外で判断しない。権限のない利用者に未完了の必須の作業を示すかどうか（情報の機密性）。
- 作業結果が変わったとき（ほかの利用者の操作、削除）の再取得。
- サンプルデータの保存の領域の分離、削除、処理の対象からの除外。
- 招待の検証、権限の検査、変更の要求の冪等性（要求の ID）と、要求の ID による処理の照会（バックエンド）。

## 独自に判断した事項

| 判断 | 理由 |
| --- | --- |
| 作業が 1 件以下の場合は Checklist を使わない（`minTasks` の既定 2） | 指示書の「複数の初期作業が必要な場合のみ」を判定にした。閲覧者や、組織の作業が完了した組織に招待されたメンバーは、Checklist を表示しない |
| 招待されたメンバーには、組織で完了済みの作業を表示しない（完了として数えることもしない） | 他人が行った作業を自分の進捗として示すと、件数と意味がずれる。組織で完了していない作業は、権限があれば表示する |
| `requirementsMet` は、すべての作業の定義から判定する（権限のない作業を含む）。権限のない作業は `outstandingRequiredWithoutPermission` に分ける | 初期実装では「この利用者が行える必須の作業だけ」で判定していたため、メンバーでは支払い方法が未登録でも `true` になり、製品が利用の制限の解除に使うと誤る。Checklist に表示しない（作業として求めない）ことと、要件を達成したことは別である |
| 対象の作業が 0 件の場合と、すべて完了した場合を区別する（0 件は `progress: "none"`、`presentation: "none"`。`minTasks` が 0 でも Checklist を表示しない） | 0 件の利用者は作業をしていないため、「利用開始の準備が完了しました」と示すと事実と異なる。`progress` を `completed` にすると、製品が Onboarding の完了の判断や計測に使った場合に、作業をしていない利用者を完了として数える。初期実装では 0 件を `not-started` にしており、`minTasks: 0` では空の Checklist を表示していた。必須の条件は、0 件でも `requirementsMet` で別に判定する |
| Contextual Help の閉じた状態は、アカウント単位で持つ | 案内は製品の操作の説明で、組織のデータに依存しない。組織を切り替えるたびに同じ案内を表示すると、繰り返しが負担になる |
| 確定した失敗だけを失敗とし、ほかの例外は結果が不明として扱う | 通信の例外を確定した失敗にすると、サーバーで処理が終わっていても新しい要求の ID で再実行でき、取り込みや招待が重複する。Forms & Workflows の `FormSaveError` の既定値と合わせた |
| 支払い方法を必須の作業にした（プレビューの `requiredTaskIds`） | model.ts の作業に必須の区別がないため。「特定の機能を使うときに必要な設定」の例として、非表示と要件の区別を示す |
| すべて完了した後は、完了を短く示して閉じられるようにし、自動では消さない | 完了したことを確かめられるようにする。閉じた後は表示しない |
| `getSetupStatus` は、途中の入力を保存していない間は「未開始」とする | 保存していない入力は、再読み込みや別の端末で再開できないため |
| 「自分だけで使う」の分岐で、招待の手順を除く | 実際の体験を変える質問の例。業種や規模の質問は置かない |
| 初回利用の Empty State の間は、検索欄と Contextual Help を置かない | 検索する対象がない。案内を 1 つにする |
| 保存の要求に AbortSignal を渡さない（取得の要求には渡す） | 中止しても、サーバーで処理されることがある。結果の反映は `useScopeGuard` で防ぐ |
| 結果が不明な操作は、確認の操作に置き換え、確認で処理されていなかった場合だけ再実行を許す | 同じ要求の ID で送り直すことも冪等にはなるが、利用者が処理の結果を知らないまま操作を繰り返さないよう、確認を先にした。確認では実際の処理の有無を照会し、作業結果も取得し直す |
| 狭い領域では Checklist の作業の補足の説明を省く（Container Query、28rem 未満） | 通常の操作の領域を圧迫しない。作業名とボタンは残す |
| 新しい組織（`new`）を Onboarding のプレビューだけの例として加えた | model.ts の組織（本社営業部、西日本営業部）は利用中のため、作成した直後の状態を示す組織が必要だった |
| 西日本営業部の顧客を 48 件とした（模擬のサーバー） | model.ts の通知「顧客の取り込みが一部失敗しました（成功 48 件、失敗 2 件）」と合わせた |

## 統合時に確認する事項

この節を書いた時点（v0.1）では、Forms & Workflows は未統合だった（`origin/feat/forms-and-workflows-patterns`、確認した版は 40df108）。その後 main に統合され、このブランチに取り込んだ（system-and-account.md の `b5ea769`）。Patterns Integration Review（2026-11-28）で、顧客の登録の Sheet の破棄の確認を `DiscardChangesAlert` に、組織の作成（`CreateOrganizationSetup`）を Multi-step Workflow の部品に置き換えた。

- **Multi-step Workflow（`useStepFlow`、`Stepper`）、Create & Edit（`useFormState`、`handleSubmit`）、Unsaved Changes（`useUnsavedChanges`、`DiscardChangesAlert`）**：組織の作成を次のように置き換えた（Patterns Integration Review の 2 回目、`fix/pi-system2`）。
  - 手順の並びと移動：`setupStepsOf` は `StepDefinition` の配列を返し、`useStepFlow({ steps, isComplete, initial })` に渡す。独自の `moveTo` と、表示中の手順が不要になった場合の `steps.includes(draft.step) ? draft.step : "data"` は廃止し、`useStepFlow` の規則に合わせた。`isComplete` は、手順の項目が `form.blockers` に含まれないこと。
  - 入力の値と送信の対象：`useFormState` の 1 つのフォームで、組織名、使い方、招待、データの始め方と `skipInvite`（任意の招待の手順をスキップした）を持つ。招待の項目は `active: usage === "team" && !skipInvite` で、自分だけで使う場合とスキップした場合に検証と送信から除く（値は残す）。スキップと、入力がないままの「次へ」は `skipInvite` を変えた後の描画で進む。スキップした後に招待を入力し直すと、送信の対象に戻す。
  - 位置の表示：「手順 n / m・必須」を、簡易の `Stepper`（`currentLabel="hidden"`）と、見出しの直後の必須・任意の文に置き換えた（上の「組織の作成」）。`StepDefinition` に必須の区別がないため、任意の手順の `label` に「（任意）」を含めた。
  - 途中の入力と再開：模擬のサーバーの `SetupDraft`（`step`、`values`、`skipped`、`requestId`）は変えていない。手順を移った後に、その時点の値を保存し、保存できた値を `form.markSaved` で基準値にする。再開では、下書きの `step` から `initial`（`current`、`reached`、手前の手順を `completed`）を作る。フォームは利用者と作成の要求の ID ごとに作り直す（`key`。新しいスコープは `initialValues` から始める）。
  - 最終の送信：`handleSubmit` で二重の実行を防ぐ。確定した失敗（`MockRequestError`）は `failed`、それ以外の例外は `unknown`。`unknown` の間は `handleSubmit` が送信しない。「作成されたかを確認する」（`findCreated`）の結果を `form.resolveUnknown` で反映する。作成の後の移動は `onSuccess`（世代が変わっていない場合だけ呼ばれる）で行い、閉じた後の応答では移動しない。
  - 保ったもの：手順の見出しへのフォーカス（`flow.headingRef`。最初から入力し直した後も見出しへ移す）、作成の要求の ID、作成の後に成功の画面を挟まないこと、必須の手順と任意の手順の区別、簡易の表示で手順の名前と見出しを重ねないこと。
  - 確定した仕様の変更（v0.1 の確定候補からの変更）：
    | 変更 | 理由 | 影響 | 検討した代替案 |
    | --- | --- | --- | --- |
    | 「次へ」を押してからエラーを示す動作を、完了するまで「次へ」を押せない動作（Focusable Disabled と理由の文、Enter でのエラーの表示）に変えた | Multi-step Workflow の確定した規則（「未完了の次へを押させてからエラーを示す」はアンチパターン）に合わせる | 組織名が空の間とメールアドレスの形式が誤っている間は、「次へ」を押せない。検品の `required vs optional, validation…` の期待値を変えた | 独自の検証を残す（Forms & Workflows と操作が異なるため採らない） |
    | 位置の表示を「手順 n / m・必須」から「ステップ n / m」（Stepper）と必須・任意の文に変えた | 正式な Stepper の文言に合わせ、完了した手順への直接の移動（「すべての手順」）を加える | 検品の `onb-setup-position` を `onb-setup-stepper` と `onb-setup-requirement` に変えた | Stepper の横に「必須」の文字を加える API を足す（Registry の API を増やす利益が小さいため採らない） |
    | 「最初から入力し直す」を確認の後にし、作成の結果が不明な間は押せないようにした | 以前は確認なしで保存した途中の入力を削除し、結果が不明な状態を解いて新しい要求の ID を作っていた。サーバーで作成されていた場合に、同じ組織を二重に作成できた | 最初から入力し直す前に `DiscardChangesAlert` が開く | 押せる状態のまま、新しい要求の ID を作らない（入力し直した内容を前の要求の ID で送ると、前の結果が返るため採らない） |
    | 「画面を閉じる」で、前回の手順の保存の後の入力を確かめるようにした | 以前は確認なしに閉じ、現在の手順の入力が失われていた | 入力した直後に閉じると「変更を破棄しますか？」が開く | 閉じる前に下書きを自動で保存する（保存の失敗と結果の不明の扱いが増えるため、この例では採らない） |
- **Create & Edit、Unsaved Changes**：顧客の登録の Sheet は `DiscardChangesAlert` を使う（`useUnsavedChanges` への登録は未実施。Sheet を閉じる操作の確認だけ）。
- **Import & Export（`import-review.tsx` の `ImportResultSummary`、`importOutcome`）**：「既存の顧客を取り込む」の画面は、模擬の CSV を取り込むだけの例である。統合後は Import & Export の画面へ移るようにし、完了は取り込みの結果（成功した件数が 1 件以上）で判定する。
- **即時の保存（`save-modes.ts` の `useInstantSave`）**：Checklist の表示の状態の保存（`useGettingStarted` の `setVisibility`）は、即時の保存と同じ性質（保存中、失敗、結果が不明、確認）を持つ。統合後に `useInstantSave` と比べ、共通化に価値がある場合だけ置き換える。世代の管理（`useScopeGuard`）と責務が重なる箇所も、統合後に比べる。
- **Authentication**：`resolveFirstScreen` の前後の遷移（認証の後の戻り先、多要素認証の設定の画面）を [authentication.md](authentication.md) と合わせる。
- **Settings**：初期値（表示言語、タイムゾーン、組織の標準）と、利用開始の後に変える画面を [settings.md](settings.md) と合わせる。
- **Permission States**：権限のない作業を表示しない判定（作業の `permission`）と、権限が変わった直後の描画を [permission-states.md](permission-states.md) と合わせる。権限の再確認中（`refreshing`、`stale`）に Checklist の対象を前の権限で導かない（統合の検証画面は `useGettingStarted` の `pending` で接続した。下の「統合の検証画面」）。
- **統合の検証画面（`#/account-app`）**：Patterns Integration Review の 2 回目で、次のように接続した。
  - 作業結果は、製品のデータから作って `useGettingStarted` の `results` に渡す（ONB-2）。最初の顧客は顧客の一覧（権限の模擬のサーバーの `fetchOverview` の件数）、既存の顧客の取り込みは処理の状況（System States の模擬のサーバーの `listJobs` に、1 件以上を取り込んだ取り込みがある）、メンバーの招待は組織のメンバー（`fetchOverview` の `members` が 2 人以上）から判定する。Onboarding の模擬のサーバーの作業結果（`getResults`）は使わない。製品のデータを取得している間は `results: null`（Checklist を導かない）、取得の失敗は `resultsError`。
  - 作業の画面と、完了を判定する製品のデータがない作業は、対象にしない（`tasks`）。支払い方法の登録とプロフィールの写真の設定は、この検証画面に画面がない。以前は「支払い方法を登録する」が支払いの設定のない組織の設定へ、「プロフィールの写真を設定する」が写真の設定のないプロフィールへ移っていた。支払い方法の必須の作業と `requirementsMet` の表示は、`#/onboarding` の例で確かめる（この検証画面では、必須の条件による利用の制限を示さない）。
  - 権限の取得中、再確認中、確認の失敗の間は、前の権限から対象の作業を導かず、Checklist の代わりに理由（「最新の権限を確認しています。確認できるまで、利用開始の準備を表示しません。」）を示す（`pending`。ONB-1）。作業のボタンと「はじめにやることを表示」も示さない。確認が終わると、新しい権限で導き直す（閲覧者には対象の作業がなく、Checklist を表示しない。0 件を完了と示さない）。
  - 作成した直後の組織（`new`）は、`MinimalShell` の中の `OnboardingProduct` だけで表示する（ONB-3。プレビューの制約）。`model.ts` の組織と所属（本社営業部、西日本営業部）に新しい組織を加えると、権限、設定、通知、System States の模擬のサーバーのすべてに組織を加える必要があり、変更の範囲が大きいため、App Shell の中の製品の画面には接続していない。

### 時間に依存しない検品

模擬のサーバーの `holdWhen`（条件に合う要求を保留する）と `releaseHeld`（解放し、応答の処理と画面の更新を待つ）で、応答の順序を検品の側で決める。固定の待ち時間（`waitForTimeout`）は使わない。初期実装にあった 4 か所（アンマウントの後の応答、作業のボタンで完了にならないこと、A → B → A、再マウントの後の案内）は、それぞれ保留と解放、変更の要求が送られていないことの確認、閉じた案内の取得の完了（`onb-product` の `data-help="ready"`）を待つ方式に変えた。`open()` は模擬のサーバーの応答の時間を 40ms にしているが、期待値は応答の時間に依存しない。

### 実施した検品と既知の制約

- 実施：`npm run typecheck`（Onboarding の担当のファイルに型の誤りがないこと。ほかの領域のファイルの誤りは、並行して編集中のため対象外）。`PREVIEW_TEST_PORT=5206 npx playwright test -c preview/playwright.config.ts system-account-onboarding --workers=2`（desktop、mobile、webkit）。
- 実機（iOS Safari、Android）とスクリーンリーダー（VoiceOver、NVDA）による確認は行っていない。
- 試用期間の終了による機能の制限は模擬していない（要件の判定と表示だけを示す）。
- 作業結果が後から未完了に戻る場合は、単体の検品（`deriveChecklist`）だけで確かめた。模擬のサーバーには、支払い方法や顧客を削除する操作を置いていない。
