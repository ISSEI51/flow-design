# Onboarding

利用者が最初の価値を体験するまでの時間を短くする。機能の説明より、実際の利用を優先し、必要な知識は使うときに示す。

状態：初期実装（レビュー前。v0.1 確定ではない） ・ 実装：[`registry/patterns/onboarding.ts`](../../../registry/patterns/onboarding.ts)、[`registry/patterns/getting-started.tsx`](../../../registry/patterns/getting-started.tsx)、[`registry/patterns/contextual-help.tsx`](../../../registry/patterns/contextual-help.tsx) ・ 全体：[System & Account](system-and-account.md)

## 目的

認証の後、利用者が迷わずに製品を使い始め、最初の価値（例：最初の顧客を登録し、一覧で確かめる）に早く届くようにする（原則 01、07）。自明な機能を 1 つずつ説明せず（原則 04）、利用開始に必要のない設定や質問で利用を妨げない。一方で、利用を続けるために必要な作業（支払い方法など）は、案内を閉じても見えなくしない（原則 08）。

## 使用条件

| 部品・方式 | 使う場合 | 使わない場合 |
| --- | --- | --- |
| 独立した初回の画面 | 組織の作成、招待の承諾、利用開始の前に必要な設定（組織のポリシーで必須の多要素認証など） | 歓迎の文と「始める」だけの画面 |
| 組織の作成（複数の手順） | 意味のある手順が複数ある場合 | 組織名だけで作成できる場合（1 画面にする） |
| Getting Started Checklist | 製品の利用につながる初期作業が複数（目安 3〜5 件）ある場合 | 作業が 1 件以下の場合（`presentation` が `none`）。招待されたメンバーで、組織の作業が完了している場合 |
| 初回利用の Empty State | 一覧などにデータがまだない場合 | 検索結果 0件、取得失敗（それぞれの表示にする） |
| Contextual Help | その操作を使える状態で、知っておくと迷わずに済む短い情報がある場合 | 見ればわかる操作の説明 |
| Product Tour | 複雑な専門機能で、説明によって学習の負荷が下がる場合だけ検討する | 標準では使わない。自明なボタンや検索欄を順番に説明しない |
| サンプルデータ | 価値の体験に実際のデータの構造が必要で、利用者が明示的に選んだ場合 | 自動で入れる。実際のデータに混ぜる |

| 要素 | 部品 | 内容 |
| --- | --- | --- |
| 初回の画面の決定 | `resolveFirstScreen`（`onboarding.ts`） | `product`、`accept-invitation`、`create-workspace`、`required-setup` のどれかを返す。歓迎の画面は返さない |
| 組織の作成 | プレビューの `CreateOrganizationSetup`（既存の `Field`、`Input`、`RadioGroup`、`Textarea`、`Button`、`Alert`） | 最小限の手順の画面。Multi-step Workflow の統合後に置き換える（「統合時に確認する事項」） |
| Getting Started Checklist | `deriveChecklist`（`onboarding.ts`）、`GettingStartedChecklist`（`getting-started.tsx`） | 完了した件数、進捗、作業の画面への移動、折りたたみ、非表示、すべて完了の表示 |
| 初回利用の Empty State | 既存の `Empty`、`getBrowseViewState`（Data Browsing） | 何ができるか、最初に何をするか、どこから操作するか |
| Contextual Help | `ContextualHelp`（`contextual-help.tsx`）、`pickGuidance`（`onboarding.ts`） | 画面の流れの中の短い案内。閉じられる |
| 初期設定の状態 | `getSetupStatus`（`onboarding.ts`） | 未開始、進行中、中断、スキップ、完了 |

### 初期設定の 3 種類

| 種類 | 例 | 求める場所 |
| --- | --- | --- |
| 利用開始の前に必要な設定 | 組織名（組織を作成する場合）、組織のポリシーで必須の多要素認証 | 初回の画面。これがないと利用を始められないものだけ |
| 利用開始の後でも可能な設定 | 表示言語、タイムゾーン、通知、プロフィールの写真 | 求めない。合理的な初期値（組織の標準、端末の設定）で始め、設定の画面で変える |
| 特定の機能を使うときに必要な設定 | 支払い方法（試用期間の終了時）、外部のカレンダーとの連携 | その機能を使う画面。Checklist に作業として示してもよい |

- 利用目的、業種、組織の規模などの質問は、実際の体験を変える場合だけ求める（例：「チームで使う／自分だけで使う」で招待の手順を省く）。
- マーケティングの目的の質問（製品を知ったきっかけなど）を、必須の設定に混ぜない。尋ねる場合は任意にし、利用開始の後に回す。

## バリエーション

| 利用者 | 初回の画面 | Checklist | Empty State |
| --- | --- | --- | --- |
| 新規登録して組織を作成した管理者 | 組織の作成 | 組織単位とアカウント単位の作業（5 件） | 登録、取り込み、サンプル |
| 既存の組織に招待されたメンバー | 招待の承諾 | 組織で完了済みの作業を除く。権限のない作業を除く（例：メンバーは招待と支払いを除く） | 組織にデータがあれば一覧を表示する |
| 招待された閲覧者 | 招待の承諾 | 作業が 1 件以下のため使わない | 登録の操作を置かない |
| 所属する組織がある利用者 | 利用画面へ直接移る | 完了または非表示なら表示しない | 通常の表示 |

## 動作

### 初回の画面

- 認証の後は、原則として製品の利用画面（最初の価値を体験する画面）へ直接移る。認証の後の戻り先（直前のページ）の扱いは [authentication.md](authentication.md) に従う。
- 独立した画面は、組織の作成、招待の承諾、利用開始の前に必要な設定のように、利用者が判断や入力をする意味がある場合だけ挟む。
- 歓迎するだけの画面、作成の後の成功の画面を挟まない。

### 組織の作成

- 手順ごとに「手順 2 / 3・任意」のように、位置と必須・任意を文字で示す。必須の項目は組織名だけにする。
- 任意の手順は「スキップ」で飛ばせる。入力がないまま「次へ」を押した場合もスキップとして扱う。スキップした作業（メンバーの招待）は、Checklist に作業として残る。
- 「戻る」で前の手順に戻っても、入力は残る。
- 途中の入力は、手順を移るたびに製品が保存する（プレビューでは模擬のサーバー）。画面を閉じた、再読み込みした、別の端末で開いた場合は、続きの手順から再開し、「前回の入力の続きから再開しています」と示す。最初から入力し直すこともできる。
- 分岐で不要になった手順（「自分だけで使う」を選んだ場合の招待）は、手順の数から除き、入力していた内容を送信しない。
- 手順を移ったら、その手順の見出しにフォーカスを移す。
- 作成の要求は二重に送らない（実行中は受け付けない。要求の ID を付け、同じ ID は 1 回だけ処理する）。
- 作成に失敗した場合は、入力を残して Alert（`role="alert"`）で示す。結果が不明な場合（通信が途中で切れた）は、もう一度作成するボタンを止め、「作成されたかを確認する」で確かめてから、作成されていれば利用画面へ、作成されていなければ再び作成できるようにする。
- 作成した後は、成功の画面を挟まずに利用画面へ移る。「サンプルデータで試す」を選んだ場合は、サンプルの領域を表示する。

### Getting Started Checklist

- 完了は、製品が渡す実際の作業結果（完了した作業の ID）だけで判定する。例：顧客を実際に登録したら「最初の顧客を登録する」が完了する。作業のボタン（「顧客を登録」「支払いの画面へ」）は作業の画面へ移る操作であり、押しただけでは完了にしない。登録の Sheet を開いて閉じた場合も完了にしない。
- 作業のボタンの名前は、押した結果（移る先や開く画面）がわかる名前にする（`actionLabel`）。
- 完了した件数（「5 件中 2 件完了」）と進捗（Progress）を示す。状態は「完了」の文字と、支援技術向けの「完了：」「未完了：」でも伝え、色とアイコンだけで伝えない。
- 折りたたみ（件数と進捗だけ）、非表示、再表示ができる。再表示の入口は、非表示にしても場所の変わらない所（画面の上部、ヘルプのメニューなど）に置く。
- 非表示は表示の状態であり、完了ではない。非表示にしても `progress` と `requirementsMet` は変わらない。必須の作業（支払い方法）が残っている場合は、非表示にした後も Alert で示し続ける。
- すべて完了した場合は、「利用開始の準備が完了しました」と短く示し、「閉じる」で非表示にできる。閉じた後は表示しない。
- 権限のない作業は表示しない（作業の `permission`）。招待されたメンバー（`audience: "invited"`）には、組織で完了済みの作業を表示しない（設定済みの項目を再設定させない）。
- アカウント単位の作業（プロフィールの写真）と組織単位の作業（顧客、取り込み、招待、支払い）を分ける。組織単位の作業は、誰が行っても組織で完了になる。アカウント単位の作業は、ほかの組織でも完了のまま示す。
- 作業が完了したら、Checklist の中に常に置いた読み上げの領域で「「最初の顧客を登録する」が完了しました。5 件中 2 件が完了しています」と伝える。最初の表示と、利用者・組織の切り替え（`scopeKey`）では読み上げない。

### 初回利用の Empty State

- 既存の `Empty` を使い、何ができるか（「顧客を登録すると、商談と契約の記録を始められます」）、最初に何をするか、どこから操作するか（「ページの上部の「顧客を登録」から」）を短く伝える。
- Page Header に同じ操作（「顧客を登録」）がある場合は、Empty に同じボタンを置かない。ほかの始め方（「CSV から取り込む」「サンプルデータで試す」）だけを置く。
- 未登録、検索結果 0件、取得失敗を区別する（Data Browsing の `getBrowseViewState`）。検索結果 0件は「条件に一致する顧客はいません」と「検索をクリア」、取得失敗は `DataRegionError` と再試行にする。取得失敗を初回利用の Empty にしない。
- データがまだない間は、検索欄を置かない（検索する対象がない）。
- 登録の権限がない利用者には、登録の操作を置かず、「登録されると、ここに表示されます」と示す。

### Product Tour

- 強制的な Tour は標準にしない。初回のログインで自動的に始まり、終わるまで操作できない Tour を作らない。
- 複雑な専門機能など、説明によって学習の負荷が下がる場合だけ検討する。利用者が自分で開始し、途中で終了し、必要に応じて続きから再開できるようにする。
- 汎用の Product Tour の仕組みは、このリリースでは提供しない（14 章の対象外）。

### Contextual Help

- 関係する操作の近くに、画面の流れの中に置く（`role="note"`）。入力欄やボタンを覆わない（Popover やモーダルにしない）。表示したときにフォーカスを奪わない。
- その操作を使える状態のときだけ表示する（例：顧客の検索の案内は、顧客が 1 件以上あり、検索語が空のときだけ）。
- 閉じるボタン（「この案内を閉じる」）を置く。閉じたときにフォーカスが案内の中にあった場合は、関係する入力欄に移す（`focusAfterDismiss`）。
- 閉じた状態はアカウントごとに保存し、再読み込みや別の端末でも表示しない（製品の責務）。保存した状態の取得が終わるまでは表示しない（閉じた案内が一瞬表示されない）。保存に失敗しても、その画面の間は表示しない。
- 重要な情報を一度だけの案内に置かない。項目の説明（`FieldDescription`）やヘルプのページにも置く。

### サンプルデータ

- 利用者が明示的に選んだ場合だけ用意する（組織の作成の最後の手順、初回利用の Empty State の「サンプルデータで試す」）。
- サンプルを表示している間は、画面の上部に「サンプルデータを表示しています」を常に示し、行にも「サンプル」と示す。件数も「サンプル 4 件」と区別する。
- 実際のデータと別の領域に保存する。サンプルへの登録は、実際の顧客の件数、利用開始の準備（Checklist の完了）、集計、請求、通知、外部への送信の対象にしない。
- 「実際のデータに戻る」と「サンプルを削除」を、サンプルの表示の上部に常に置く。実際のデータの表示からも「サンプルを表示」で戻れる。
- 見た目のラベルだけでは分離にならない。保存の領域、検索、集計、通知、外部への送信、請求の処理で分けることは製品の責務である。プレビューでは、模擬のサーバーの中でサンプルの領域（`sample`）を分け、サンプルからの操作が実際のデータに伝わらないことを検品している。

### 結果が不明な操作

作業の画面の変更の操作（顧客の登録、取り込み、招待、支払い方法、プロフィールの写真、サンプルの用意と削除、招待の承諾）は、組織の作成と同じ規則で扱う（[system-and-account.md](system-and-account.md) の共通の状態管理と安全性）。

- 実行中は同じ操作を受け付けない（ボタンは Loading）。
- 操作ごとに要求の ID を付ける。バックエンドは同じ ID の要求を 1 回だけ処理する（冪等）。プレビューの模擬のサーバーも、要求の ID で 1 回だけ処理する。
- 結果が不明な場合（応答が届かなかった）は、成功として表示しない。同じ操作のボタンの代わりに「処理されたかを確認する」を置き、もう一度実行させない（Enter で送信した場合も確認になる）。あわせて作業結果を取得し直し、実際の状態を表示する。
- 確認では要求の ID を照会する。処理されていれば成功として扱い（「処理されていました。3 件を取り込みました。」）、処理されていなければ、もう一度実行できるようにする（「処理されていませんでした。もう一度行えます。」）。確認にも失敗した場合は、確認の操作を残す。
- 顧客の登録の Sheet では、結果が不明な場合も Sheet を閉じず、Sheet の中で結果と確認の操作を示す。

### 同時に示す案内

- 同時に表示する案内は 1 つにする（`pickGuidance`）。Empty State を表示している領域には、Contextual Help を出さない。
- Checklist は通常の操作の領域を圧迫しないよう、折りたたみと非表示を提供し、狭い領域では作業の補足の説明を省く。

## アンチパターン

| 避ける | 理由 | 代わりに |
| --- | --- | --- |
| 認証の後に歓迎の画面を挟む | 押す以外にすることがなく、利用までの手順が増える | 利用画面へ直接移る |
| 作成の後に「作成しました」の画面を挟む | 利用までの手順が増える | すぐに利用画面へ移る |
| マーケティングの質問を必須にする | 利用開始を妨げる | 任意にし、利用開始の後に回す |
| 後から設定できるものを最初に求める | 最初の価値体験が遅れる | 初期値で始め、設定の画面で変える |
| Checklist の項目をチェックで完了にする | 作業をしていなくても完了になる | 実際の作業結果で判定する |
| 非表示にしたことを要件の達成として扱う | 必須の作業が残ったまま見えなくなる | 進捗と要件を表示と別に持ち、残った必須の作業を示す |
| 権限のない作業を Checklist に出す | 押しても行えない | 権限で絞り込む |
| 招待されたメンバーに組織の設定を再び求める | 設定済みのことを繰り返させる | 組織で完了済みの作業を示さない |
| Page Header と Empty State に同じ操作を置く | どちらを押すか迷う | 操作は 1 か所にし、Empty では場所を示す |
| 初回利用の Empty と検索結果 0件を同じ表示にする | 次にすべき操作が異なる | `getBrowseViewState` で区別する |
| 自明なボタンを順番に説明する Tour | 見ればわかることを説明し、操作を止める | 必要な場所の短い Contextual Help |
| 閉じた案内を次の訪問で再び表示する | 繰り返しが負担になり、案内を読まなくなる | 閉じた状態をアカウントごとに保存する |
| サンプルを実際のデータに混ぜる | 集計、請求、送信の対象になる | 別の領域に保存し、常に識別できるようにする |
| 案内を複数同時に表示する | どれを読むか迷い、操作の領域が狭くなる | 1 つにする |
| 結果が不明な操作を、そのままもう一度実行できる | 取り込みや招待が重複する | 確認の操作だけを置き、要求の ID を照会する。バックエンドは要求の ID で冪等にする |
| 演出のための待ち時間やアニメーション | 不要な待ち時間 | すぐに利用画面を表示する |

## 状態管理

| 状態 | 意味 | 持つ値 |
| --- | --- | --- |
| 未開始 | 作業や手順を、まだ 1 つも始めていない（保存した途中の入力がない） | `progress: "not-started"`、`getSetupStatus` の `not-started` |
| 進行中 | 一部が完了している、または途中の入力を保存して手順の画面を操作している | `in-progress` |
| 中断 | 途中の入力が保存されていて、手順の画面を閉じた（再読み込み、別の端末を含む）。続きから再開できる | `interrupted` |
| スキップ | 任意の手順を行わないことにした。完了ではない（Checklist に作業として残る） | 製品が保存する手順の ID（プレビューの `SetupDraft.skipped`）、`getSetupStatus` の `skipped`（任意の設定の全体を行わないことにした場合） |
| 非表示 | 利用者が Checklist を非表示にした。表示の状態であり、進捗は変わらない | `visibility: "hidden"` |
| 完了 | 実際の作業結果で、すべての作業が完了した。組織の作成では、作成した | `progress: "completed"`、`completed` |

- 進捗（`progress`、`requirementsMet`）と表示（`visibility`、`presentation`）を別の値で持つ。1 つの Boolean（`onboardingDone` など）にまとめない。
- アカウント単位の進捗（`results.account`）と組織単位の進捗（`results.workspace`）を分けて渡す。`deriveChecklist` は、作業の `scope` と異なる範囲の結果を完了として数えない。
- 表示の状態、スキップ、途中の入力、閉じた案内は製品が保存する（サーバーなど）。ページの再読み込みや別の端末で、初期状態に戻さない。Registry の部品は状態を保存しない（LocalStorage、URL、Cookie に依存しない）。
- 利用者、組織、権限が変わったら、前の利用者の Checklist を 1 回の描画でも表示しない。プレビューでは、取得に `useBrowseData`（`scopeKey` に利用者、組織、権限）、表示の状態の保存に `useScopeGuard` を使い、A → B → A と切り替えても、最後の A の結果だけを反映する。
- 保存の要求（表示の状態、閉じた案内、途中の入力、作成）は、画面を閉じても中止しない（中止しても、サーバーで処理されることがあるため）。結果は、開始したときのスコープの最新の要求にだけ反映し、アンマウントの後は反映しない。
- 表示の状態の保存に失敗した場合は、保存されている状態に戻して知らせる。結果が不明な場合は、保存されている状態を取得し直す。
- 作業の変更の操作の結果が不明な場合は、操作ごとに「確認が必要」（要求の ID）を持ち、確認が終わるまで同じ操作を実行しない（プレビューの `useActions`）。確認が必要な状態も、開始したときのスコープの中だけで持つ。

### deriveChecklist の値

| 値 | 意味 |
| --- | --- |
| `items` | 表示する作業（権限と利用者の種類で絞り込んだもの）。`done`、`required`、`scope` を持つ |
| `doneCount`、`total` | 完了した件数と、表示する作業の件数 |
| `progress` | `not-started`、`in-progress`、`completed` |
| `visibility` | 利用者が選んだ表示（`expanded`、`collapsed`、`hidden`） |
| `presentation` | 実際に表示する形（`none`、`hidden`、`completed`、`expanded`、`collapsed`）。上の図の表の順に判定する |
| `requirementsMet`、`outstandingRequired` | この利用者が行える必須の作業が完了したか、完了していない必須の作業。非表示にしても変わらない |

## 評価指標

計測の仕組み（イベントの収集、分析の基盤）は、このリリースでは提供しない。製品が最初の価値体験を定義し、次の判断基準で評価する。チュートリアルや Tour の完了率だけで品質を判断しない（完了しても価値を体験していない場合がある）。

| 指標 | 定義 | 判断の基準 |
| --- | --- | --- |
| Time to First Value | 登録から、製品が定義した最初の価値体験までの時間 | 短いほどよい。長い場合は、利用開始の前の設定と質問、待ち時間を見直す |
| Activation Rate | 登録した利用者のうち、最初の価値体験に達した割合 | Checklist の完了ではなく、価値体験の到達で数える |
| Setup Completion Rate | 必須の初期設定を完了した割合 | 任意の手順のスキップを失敗に数えない |
| Step Drop-off | 手順ごとの離脱の割合 | 離脱の多い手順は、必須か、後に回せるか、質問が必要かを見直す |
| Onboarding 後の継続率 | 最初の価値体験の後も使い続けている割合（例：1 週間後、4 週間後） | Onboarding の変更の効果は、継続率で確かめる |

## アクセシビリティ

| 用途 | 指定 |
| --- | --- |
| Checklist | `<section aria-labelledby>`（見出し）。折りたたみのボタンは `aria-expanded` と `aria-controls`。作業の状態は「完了：」「未完了：」（支援技術向け）と「完了」の文字 |
| 進捗 | Progress（`aria-valuetext` に「5 件中 2 件完了」）。件数は文字でも示す |
| 作業の完了 | Checklist の中に常に置いた `role="status"`。新しく完了した作業だけを読み上げる。最初の表示と切り替えでは読み上げない |
| 画面の移動 | プレビューの製品の画面では、`role="status"` で「支払いの画面を表示しています」と伝える。フォーカスは押したボタンに残す |
| 組織の作成 | 手順を移ったら、手順の見出し（`tabIndex={-1}`）にフォーカスを移す。失敗と結果の不明は `role="alert"` |
| Contextual Help | `role="note"`。閉じるボタンは「この案内を閉じる」。閉じた後のフォーカスは関係する入力欄へ |
| 非表示と再表示 | 非表示にしたら再表示の入口へ、再表示したら Checklist（`tabIndex={-1}`）へフォーカスを移す（`<body>` に落とさない） |

- キーボード、タッチ、スクリーンリーダーで、すべての操作ができる。ボタンの高さは 40px 以上（`size="sm"`）、主要な操作は 48px。
- 状態の変化でフォーカスを奪わない。Checklist の完了の読み上げは polite。
- 動きを減らす設定では、Sheet の移動などの動き（既存の Components の `motion-safe:`）を止める。Onboarding のための待ち時間やアニメーションは置かない。
- 実機（iOS Safari、Android）とスクリーンリーダー（VoiceOver、NVDA）による確認は、まだ行っていない。

## セキュリティ上の注意

- 権限のない作業を Checklist に表示しないのは表示の制御であり、認可ではない。作業の画面と API で、バックエンドが権限を確かめる。
- 招待の承諾では、招待のトークンの検証、期限、招待された宛先と認証した利用者の一致を、バックエンドで確かめる（プレビューは模擬の招待）。
- 招待のメールアドレスなどの途中の入力は、個人情報を含む。保存する場合はアカウントに結び付けてサーバーに保存し、URL、LocalStorage、ログに残さない。
- 利用者や組織を切り替えたら、前の利用者の進捗、途中の入力、閉じた案内を表示しない（`scopeKey`）。
- サンプルの領域のデータを、外部への送信、請求、正式な集計の処理に渡さない（製品のバックエンドで分ける）。
- 組織の作成、顧客の登録、取り込み、招待などの変更の要求には要求の ID を付け、同じ ID を 1 回だけ処理する（冪等性。バックエンド）。結果が不明な要求を、確認せずに新しい ID で送り直さない。

## 製品側の責務

- 状態の永続化：Checklist の表示の状態（利用者 × 組織）、閉じた案内（アカウント）、組織の作成の途中の入力とスキップ（アカウント）。
- 実際の作業結果の取得（顧客の件数、取り込み、招待、支払い方法、プロフィールの写真）と、`results.account` と `results.workspace` への振り分け。サンプルを含めない。
- 利用開始の前に必要な設定の判定（組織のポリシー、規約など）と、`resolveFirstScreen` の結果に応じたルーティング。
- 最初の価値体験の定義と計測（評価指標）。
- 必須の作業が残る場合の機能の制限（試用期間の終了時など）と、その案内。
- サンプルデータの保存の領域の分離、削除、処理の対象からの除外。
- 招待の検証、権限の検査、変更の要求の冪等性（要求の ID）と、要求の ID による処理の照会（バックエンド）。

## コードと資料の区分

| 区分 | 内容 | 理由 |
| --- | --- | --- |
| Registry のコード | `onboarding.ts`：`resolveFirstScreen`、`deriveChecklist`、`getSetupStatus`、`pickGuidance`<br>`getting-started.tsx`：`GettingStartedChecklist`<br>`contextual-help.tsx`：`ContextualHelp` | 非表示と完了の混同、別の範囲の結果の混入、権限のない作業の表示、完了の読み上げ、閉じた後のフォーカスは、製品ごとに書き直すと誤りやすい。判定は純粋な関数にし、ブラウザを使わずに検品できるようにした |
| 組み合わせの例（プレビュー） | 組織の作成、Checklist の接続、初回利用の Empty State、Contextual Help の例、サンプルデータの領域、招待されたメンバーの利用開始、小さな製品の画面 | 画面の構成と作業の内容は製品で変わる。組織の作成は Multi-step Workflow（未統合）の領域のため、Registry に置かない |

| 製品の責務 | 状態の永続化、実際の作業結果の取得、サンプルの分離、招待の検証、権限の検査、計測 | 製品の基盤に依存する |

## 独自に判断した事項

| 判断 | 理由 |
| --- | --- |
| 作業が 1 件以下の場合は Checklist を使わない（`minTasks` の既定 2） | 指示書の「複数の初期作業が必要な場合のみ」を判定にした。閲覧者や、組織の作業が完了した組織に招待されたメンバーは、Checklist を表示しない |
| 招待されたメンバーには、組織で完了済みの作業を表示しない（完了として数えることもしない） | 他人が行った作業を自分の進捗として示すと、件数と意味がずれる。組織で完了していない作業は、権限があれば表示する |
| `requirementsMet` は、この利用者が行える必須の作業だけで判定する | 権限のないメンバーに、支払い方法の未登録を作業として示さない。組織全体の要件の判定は製品が行う |
| 支払い方法を必須の作業にした（プレビューの `requiredTaskIds`） | model.ts の作業に必須の区別がないため。「特定の機能を使うときに必要な設定」の例として、非表示と要件の区別を示す |
| すべて完了した後は、完了を短く示して閉じられるようにし、自動では消さない | 完了したことを確かめられるようにする。閉じた後は表示しない |
| `getSetupStatus` は、途中の入力を保存していない間は「未開始」とする | 保存していない入力は、再読み込みや別の端末で再開できないため |
| 「自分だけで使う」の分岐で、招待の手順を除く | 実際の体験を変える質問の例。業種や規模の質問は置かない |
| 初回利用の Empty State の間は、検索欄と Contextual Help を置かない | 検索する対象がない。案内を 1 つにする |
| 保存の要求に AbortSignal を渡さない（取得の要求には渡す） | 中止しても、サーバーで処理されることがある。結果の反映は `useScopeGuard` で防ぐ |
| 結果が不明な操作は、確認の操作に置き換え、確認で処理されていなかった場合だけ再実行を許す | 同じ要求の ID で送り直すことも冪等にはなるが、利用者が処理の結果を知らないまま操作を繰り返さないよう、確認を先にした。確認では実際の処理の有無を照会し、作業結果も取得し直す |
| 狭い領域では Checklist の作業の補足の説明を省く（Container Query、28rem 未満） | 通常の操作の領域を圧迫しない。作業名とボタンは残す |
| 新しい組織（`new`）を Onboarding のプレビューだけの例として加えた | model.ts の組織（本社営業部、西日本営業部）は利用中のため、作成した直後の状態を示す組織が必要だった |
| 西日本営業部の顧客を 48 件とした（模擬のサーバー） | model.ts の通知「顧客の取り込みが一部失敗しました（成功 48 件、失敗 2 件）」と合わせた |

## 統合時に確認する事項

- **Multi-step Workflow（Forms & Workflows）**：組織の作成（`CreateOrganizationSetup`）は、既存の Components で作った最小限の手順の画面である。統合後は、手順の表示（Stepper）、必須と任意、スキップ、戻る、途中の入力の保持と再開、分岐で不要になった手順の扱いを、Multi-step Workflow の部品に置き換える。置き換えの後も、手順の見出しへのフォーカス、作成の要求の ID、結果の不明の確認を保つ。
- **Create & Edit、Unsaved Changes（Forms & Workflows）**：顧客の登録の Sheet は、既存の `Sheet` の `unsavedChanges` と、プレビューの `DiscardAlert` を使っている。統合後は Forms & Workflows の部品に置き換える。
- **Import & Export（Forms & Workflows）**：「既存の顧客を取り込む」の画面は、模擬の CSV を取り込むだけの例である。統合後は Import & Export の画面へ移るようにし、完了は取り込みの結果（成功した件数）で判定する。
- **Authentication**：`resolveFirstScreen` の前後の遷移（認証の後の戻り先、多要素認証の設定の画面）を [authentication.md](authentication.md) と合わせる。
- **Settings**：初期値（表示言語、タイムゾーン、組織の標準）と、利用開始の後に変える画面を [settings.md](settings.md) と合わせる。
- **Permission States**：権限のない作業を表示しない判定（作業の `permission`）と、権限が変わった直後の描画を [permission-states.md](permission-states.md) と合わせる。
- **統合の検証画面**：`OnboardingViewer`（利用者、組織、ロールの権限、`joinedBy`）を現在の利用者から作り、`useGettingStarted` の `results` に製品のデータから作った作業結果を渡す。

| 対象 | 検品 |
